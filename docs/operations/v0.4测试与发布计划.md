# v0.4 测试与发布计划

状态：已冻结，待实现

## 1. 测试分层

### Contract 与纯函数

- Embedding/Profile/Trace/Search Hit/Story v1-v2 Zod 正反例。
- Embedding Input 截断、Hash、Vector 有限数值、零向量、条数和维度校验。
- Ollama/OpenAI-compatible 协议 Fixture：成功、乱序、缺 Index、429、401、5xx、Timeout、非法 JSON。
- RRF：去重、通道 Rank、相同 Raw Score、稳定 Tie-break、Limit、空通道和降级 Trace。
- Story Builder：输入顺序打乱后输出一致、热点打分、阅读路线去重、Quote 上限、无图/零文件。

### PostgreSQL Integration

- 空库按 `0001..0004` 应用；v0.3 库只执行 0004；二次迁移 no-op。
- 同 Profile 并发创建只生成一个 Index/Job。
- Variable Dimension：两个 Snapshot/Profile 可分别保存 768 与 1536；同 Profile 混维度失败。
- 复合 FK 拒绝跨 Snapshot Chunk/Profile。
- Partial Batch 崩溃后复用；Hash 变化拒绝；Ready Count 不一致回滚。
- Lease Owner、过期 Lease、取消、显式重试、Attempts Exhausted。
- Text/Symbol/Semantic 查询排序和 RRF 输入固定；Semantic SQL 只扫描目标 Profile。
- 删除 Snapshot 级联 Index/Vector/Job，不影响其他 Snapshot。
- Story v1/v2 JSON 都能读取。

### API 与 Worker

- Retrieval Status 的 disabled/missing/queued/running/ready/failed/mismatch。
- Create Embedding 的 200/202 幂等、Provider disabled、Snapshot not ready。
- Worker Batch Progress、Heartbeat、取消、租约丢失、Provider Retryable/Permanent、恢复完成。
- 四种 Search Mode 使用不同 Store/Provider 路径；Semantic-only 不降级。
- Hybrid 的 index missing/provider down/dimension mismatch Trace。
- Ask 与 Search 使用相同 Retriever Fixture；伪造 Citation 仍被删除。
- Story v2 创建固定到 Snapshot，旧 v1 Share 读取不回归。
- OpenAPI Operation/Schema 与 Fastify Route 完全一致。

### CLI

- `search` 的 mode/limit/snapshot/query 验证、JSON 与人类输出。
- `embed` 的 queued/ready、`--wait`、Timeout、failed exit code。
- API Error、Request ID、Retryable 和 Usage Error 不回归。

### Web

- 组件和 Playwright 矩阵遵循[前端文档](../frontend/v0.4前端开发文档.md)。
- Chromium 固定网络 Mock 覆盖完整用户路径；真实 API 验收另行执行。

## 2. Retrieval Quality Fixture

仓库内增加一个小型、许可兼容的脱敏代码 Corpus 或由测试代码动态构造 Snapshot，至少包含：

- HTTP 路由注册；
- Response Compression Middleware；
- Database Transaction；
- Background Job Lease；
- Citation Verification。

每个 Query 记录一个或多个 Expected Evidence ID。评估输出：

- Recall@1/3/5；
- MRR@10；
- 各通道候选数；
- Hybrid 相比 Text 的变化。

确定性 Test Provider 只验证算法和 SQL，报告必须标记 `test-only`，不能成为 README 的 AI
效果数字。

## 3. 真实 Ollama 验收

本机已安装 Ollama，但发布验收必须显式拉取/确认一个拥有 Embedding Capability 的模型，例如
`nomic-embed-text`。验收记录包括：

```text
ollama version
ollama show <model>
model digest
embedding dimensions
RepoVista commit
snapshot commit
machine architecture
```

流程：

1. 在干净 v0.4 数据库应用 Migration。
2. 导入真实公共仓库（优先复用 `go-chi/chi` 的固定 Commit）。
3. 使用 `POST /embeddings` 或 CLI `embed --wait` 构建完整 Index。
4. 记录 total/embedded chunks、耗时、失败重试、数据库大小和 Query p50/p95（至少 20 次）。
5. 选择至少 5 个自然语言 Query，其中至少 2 个避免直接使用目标 Symbol/File 名。
6. 人工确认 Expected Source，记录 Text/Symbol/Semantic/Hybrid Rank 与 Trace。
7. 停止 Ollama：Hybrid 必须 degraded 且仍返回 lexical；Semantic-only 必须稳定失败。
8. 重启 API/Worker 和 Ollama：Ready Index 不重建，Query 恢复。

只有真实结果足够好时才写 README 示例；否则诚实记录限制并修复/缩小声明。

## 4. 性能与 SQL 验收

- 对 Text、Symbol、Semantic SQL 执行 `EXPLAIN (ANALYZE, BUFFERS)`，保存目标 Snapshot/Profile、
  Chunk 数和机器。
- Semantic Query 必须在 Plan 中先受 Profile/Snapshot 限制；不得全表跨 Profile Distance Sort。
- Worker 峰值内存观察至少一次，证明 Batch Loop 未同时持有全部 Vector。
- Story Builder 在真实 Snapshot 上记录运行时间与输出 JSON 大小。
- Web 首屏和 Search 结果不一次渲染超过 100 Hit。

发布不设脱离数据集的绝对性能宣传。内部建议预算：单 Snapshot 10k Chunk 下本地数据库 Query
p95 < 500ms；若未达到，记录真实数字和优化结果。

## 5. 安全验收

- Provider URL/Header 只来自配置；恶意 Path/Source 不能注入 URL、Header 或 JSON 结构。
- Error/Event/Trace/Story/Log 不包含 API Key。
- 非有限 Vector、超维度、超长 Model、超长 Query、Path Traversal 全部拒绝。
- Story Quote 以纯文本渲染；`<script>`、HTML、Markdown Link 不执行。
- Search/Ask Evidence 的 Snapshot、Commit、File、Range、Hash 归属验证。
- RepoVista 仍不安装依赖、不运行目标仓库代码、不让 AI 自动修改文件。
