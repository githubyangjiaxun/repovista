# 本地开发与部署

状态：proposal  
适用版本：v0.1

## 1. 开发环境

建议工具：Node.js LTS、pnpm、Docker、Git，以及可选的 Ollama。

仓库根目录建议：

~~~text
repovista/
├── apps/
│   ├── web/
│   ├── api/
│   ├── worker/
│   └── cli/
├── packages/
├── docs/
├── deploy/
├── examples/
├── benchmarks/
├── compose.yaml
├── pnpm-workspace.yaml
└── .env.example
~~~

## 2. 服务端口

| 服务 | 默认端口 |
|---|---:|
| Web | 3000 |
| API | 4000 |
| PostgreSQL | 5432 |
| MinIO API | 9000 |
| MinIO Console | 9001 |
| Ollama | 11434 |
| OpenTelemetry Collector | 4318 |

端口都可以通过专用环境变量覆盖。

## 3. 环境变量

`.env.example` 至少包含：

~~~dotenv
APP_ENV=development
WEB_ORIGIN=http://localhost:3000
API_ORIGIN=http://localhost:4000
DATABASE_URL=postgresql://repovista:repovista@localhost:5432/repovista
OBJECT_STORAGE_ENDPOINT=http://localhost:9000
OBJECT_STORAGE_BUCKET=repovista
MODEL_PROVIDER=none
OLLAMA_BASE_URL=http://localhost:11434
REPOSITORY_MAX_FILES=10000
REPOSITORY_MAX_BYTES=524288000
SOURCE_FILE_MAX_BYTES=2097152
JOB_TIMEOUT_SECONDS=900
~~~

真实密钥不进入 Git。生产环境由 Secret Manager 注入。

## 4. 本地启动流程

目标开发体验：

~~~bash
cp .env.example .env
docker compose up -d postgres minio
pnpm install
pnpm db:migrate
pnpm dev
~~~

全容器体验：

~~~bash
docker compose up --build
~~~

启动后：

- Web：http://localhost:3000
- API Health：http://localhost:4000/v1/health/ready
- MinIO Console：http://localhost:9001

## 5. 推荐脚本

~~~text
dev        -> 启动 Web、API、Worker
build      -> 构建所有包
lint       -> 运行代码检查
typecheck  -> 运行 TypeScript 检查
test       -> 运行单元和集成测试
test:e2e   -> 运行 Playwright
db:migrate -> 执行数据库迁移
db:seed    -> 写入本地示例数据
benchmark  -> 运行固定数据集性能测试
~~~

脚本名称是契约，README、CI 和贡献文档统一使用。

## 6. 示例数据

提供三种固定仓库 Fixture：

- tiny-ts：几十个文件，用于单元和集成测试。
- medium-ts：真实结构的中型示例，用于 E2E。
- malicious-fixtures：符号链接、超大文件、Prompt Injection 和异常路径。

开发环境 seed 只创建演示用户、工作区和已知 Snapshot，不依赖实时 GitHub 网络。

## 7. Docker Compose

基础服务：

- postgres：启用 pgvector。
- minio：对象存储。
- api：HTTP 服务。
- worker：后台索引。
- web：前端。
- ollama：optional profile。

生产镜像要求：

- 多阶段构建。
- 非 root 用户运行。
- 固定基础镜像版本。
- 只复制运行所需产物。
- 生成 SBOM。
- 镜像漏洞扫描。
- Worker 临时目录单独挂载并设置限额。

## 8. 云端部署

第一版建议单区域：

~~~text
CDN
 └── Web
      └── API
           ├── PostgreSQL
           ├── Object Storage
           └── Worker Pool
~~~

不需要 Kubernetes。可使用托管容器平台，条件是 Worker 可以独立扩缩容、支持长任务和优雅终止，数据库有备份和 PITR，对象存储私有并支持健康检查。

## 9. 发布流程

1. PR 通过所有质量门禁。
2. staging 执行 Migration 和 smoke test。
3. 人工确认地图、源码引用和问答。
4. 创建语义化版本 Tag。
5. 发布镜像和 Release Notes。
6. 生产 Migration 后滚动发布。
7. 观察错误率、队列和引用验证指标。

## 10. 优雅停止

API 停止接收新连接、等待短请求完成并关闭数据库连接池。Worker 停止领取新任务，当前任务在宽限期内完成或保存进度，无法完成时释放租约并清理临时目录。

## 11. 故障排查

### Job 一直 queued

检查 Worker readiness、数据库连接、任务 priority、租约和 workspace 并发限制。

### Job 卡在 cloning

检查 GitHub 限流、DNS、出站网络、仓库大小和临时磁盘。

### 地图为空

检查支持语言、parse_status、parser_version 和 Snapshot 状态。

### AI 有答案但没有引用

将答案视为失败，检查 evidence_id、结构化输出和 evidence_hash。

## 12. 安全运行要求

- Worker 与 API 使用不同数据库角色。
- Git 凭据按 Job 临时提供并尽快销毁。
- 临时目录不可被 Web 服务读取。
- 私有 Blob 只通过授权 API 获取。
- 对象存储禁止公共 Bucket。
- 日志统一脱敏。
- 定期轮换服务密钥。
