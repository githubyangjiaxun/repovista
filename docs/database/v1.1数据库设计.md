# v1.1 数据库设计：幂等 Demo Seed

状态：已完成验收（2026-08-27）

## 1. Schema 结论

v1.1 不新增表、列、索引或 Migration。Demo 使用现有：

- `repositories` 与 Public Workspace 唯一 canonical URL；
- `repository_snapshots` 的不可变 Commit/parser/index version；
- `analysis_jobs`、Lease 和 `job_events`；
- Blob/File/Symbol/Edge/Chunk 完整 Snapshot 数据；
- `guardrail_explanations` 的幂等唯一键与 `subject_key` 历史索引。

没有新的数据库结构，就是本版本的重要约束：Demo 必须证明正式数据模型足够，而不是建立平行的
“样例模式”。

## 2. 保留身份

Demo canonical URL 是共享 Contract 中的精确常量，只能位于固定 Public Workspace。它在 UI 中被标记
为 Bundled Fixture，不作为可克隆远端使用。Snapshot ID 和 Job ID 仍由正常 UUIDv7 生成；稳定性来自
Repository URL、Fixture revision 和 Ready Snapshot 查询，而不是硬编码主键。

## 3. 幂等规则

- Seed 前按 Repository + revision + parser version 查找 Ready Snapshot。
- 已存在则不创建 Import/Job，不重写其 Blob、File、Symbol、Edge 或 Stats。
- 缺失时通过正常 Import 创建 Snapshot/Job，并只领取返回的 Job ID。
- Explanation 继续使用
  `(workspace_id, snapshot_id, finding_fingerprint, provider, model_name, prompt_version)` 收敛。
- Base/Head 的共同 Finding 通过服务端 `subject_key` 进入同一历史，不直接写客户端提供的 Key。

重复 Seed 的数据库验收比较前后计数和目标 IDs；幂等不允许仅凭控制台文案判断。

## 4. 失败与恢复

- Seeder 中断后保留已有 Job/Snapshot 状态，由现有租约、重试和失败逻辑解释。
- 再次运行可以领取 lease 已过期的同一精确 Job，或在没有活动 Job 时创建新尝试。
- 不自动删除 Failed Snapshot，避免隐藏失败证据。
- 若发现保留 URL 已被不兼容数据占用，快速失败并要求人工检查，不执行破坏性修复。

## 5. 数据保留

关闭 `DEMO_SEED_ENABLED` 只停止后续 Seed，不删除现有 Demo。删除 Demo 仍属于显式管理员操作；v1.1
不提供自动清理命令，也不在生产 Overlay 中运行删除 SQL。
