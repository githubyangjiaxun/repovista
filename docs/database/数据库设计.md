# 数据库设计

状态：v1.0 已实现并通过独立 PostgreSQL 17 + pgvector 验收（2026-08-25）
事实来源：`packages/database/migrations/0001_initial.sql` ～
`packages/database/migrations/0008_guardrail_explanation_history.sql`

## 1. 选择

RepoVista 使用 PostgreSQL 17 作为唯一持久化和任务协调依赖。初始 Migration 启用：

- `vector`：保存 Snapshot/Profile 范围内的可变维度 Chunk Embedding；旧 `vector(1536)` 列只保留
  v0.1-v0.3 兼容，不再读写。
- `pg_trgm`：路径和符号模糊搜索索引。
- `citext`：Email 和 Workspace Slug 的大小写不敏感约束。

全文检索使用生成的 `tsvector` 和 GIN。图使用关系表邻接模型，不需要图数据库。任务队列使用
普通表、Partial Index、行锁和租约，不需要 Redis。

Migration Runner 先保证 `schema_migrations` 存在，再按文件名顺序在事务中执行未记录的 SQL。
已发布 Migration 不允许原地修改；结构演进必须新增前向文件。

## 4. Repository 与 Snapshot

### Repository

- `(workspace_id, canonical_url)` 唯一。
- Provider 当前只允许 `github`。
- Visibility 字段允许 public/private 作为演进边界，但 API 只创建 public。
- `latest_ready_snapshot_id` 外键使用 `ON DELETE SET NULL`。
- `auto_update_enabled` 默认为 false。
- `github_installation_id` 可空且必须为正数；它只是来源元数据，不是 Token。
- `last_webhook_at` 记录最近一次有效且属于该仓库的 Push。

### Snapshot

- Ready Snapshot 由应用保证具备完整 40 位 Commit SHA。
- `(repository_id, commit_sha, parser_version, index_version)` 在 Commit 非空时唯一。
- `base_snapshot_id` 是同表自引用，删除基线时 `SET NULL`。
- `index_mode` 只允许 `full/incremental`，旧数据默认 Full。
- `tree_hash` 已存在于初始 Schema；v0.2 Worker 对 Ready 新快照写入确定性值。
- `stats_json.indexing` 保存 Mode、Base Snapshot/Commit 和
  scanned/changed/reused/parsed/deleted 计数。
- `(repository_id, parser_version, ready_at DESC) WHERE status='ready'` 支持兼容基线选择。
- `workspace_id` 由 Repository 回填并与 `id` 组成复合唯一键，供 Workspace-scoped 派生记录使用；
  应用创建的每个新 Snapshot 都显式写入 Workspace。
- `guardrail_profile_id` 只在创建 Snapshot 时复制 Repository 当前绑定，后续策略切换不改历史 Snapshot。

`parent_commit_sha` 表示 Git Parent；`base_snapshot_id` 表示实际解析复用来源，两者不能混用。
JSON 统计结构由共享 Zod Contract、Store 和测试约束，数据库不为每个 JSON 字段重复建列。

## 5. 文件、Symbol 与 Edge 约束

### Snapshot File

- `(snapshot_id, path)` 唯一。
- Path 不能为空、不能是绝对路径、不能以或包含 `..` 逃逸。
- Blob Hash 外键保证 Source 内容存在。
- Parse Status 区分 parsed、skipped、failed 等扫描/解析结果。

### Symbol

- `(snapshot_id, stable_key)` 唯一。
- `start_line > 0` 且 `end_line >= start_line`。
- Stable Key 由 Parser 的文件、Kind、Qualified Name、Signature/位置规则确定。

### Edge

- 必须恰好有一种目标：`to_symbol_id` 或 `unresolved_target`。
- 已解析和未解析 Edge 分别有唯一索引，避免重试重复插入。
- Confidence 限制在 0～1。
- Snapshot Stats 的 Edge 数按数据库唯一关系口径去重，必须与实际持久化集合一致。

## 6. Job 与 Delivery 约束

### Job

- Status 只允许 `queued/running/succeeded/failed/cancelled`。
- Progress 限制在 0～1。
- `idempotency_key` 唯一。
- Claim Index 只覆盖 queued/running，Lease Index 只覆盖 running。
- 完成、失败和取消终态都必须锁定 Job 并验证 Snapshot、Worker 和 Lease Owner。
- `embed_snapshot` 必须同时拥有 Repository/Snapshot/Embedding Profile；每个 Profile 只有一个 Job。
- PR Analysis Job 用 `analysis_id` 关联；`available_at` 支持可重试退避。

### GitHub Delivery

- `delivery_id` 是长度 1～200 的主键。
- `event_name` 非空且最多 100 字符。
- `payload_sha256` 必须匹配 `sha256:<64 lowercase hex>`。
- 持久状态只允许 `enqueued/ignored`；API 可把已存在的相同请求映射为 `duplicate`。
- 同 Delivery/同 Hash 返回首次结果；同 Delivery/不同 Hash 抛出冲突。
- 有效 Push 的 Delivery、Repository Upsert、Snapshot、Job、初始 Event 和关联更新在一个事务中。

## 7. 索引

| 索引 | 目的 |
|---|---|
| Snapshot Repository + Requested At | 历史列表 |
| Snapshot Repository + Parser + Ready At partial | 增量基线 |
| File Path trigram | 文件过滤/模糊查询 |
| Symbol Name trigram | 符号检索 |
| Symbol Snapshot + Qualified Name/Kind | 图与结构过滤 |
| Chunk `search_vector` GIN | 全文证据检索 |
| Chunk Snapshot/File | 限定不可变范围和源码顺序 |
| Job Status/Priority/Created At partial | 快速 Claim |
| Job Lease Expires partial | 崩溃接管 |
| Event Job/ID | SSE 增量读取 |
| Delivery Repository/Received At partial | 仓库自动更新审计 |
| PR Analysis Repository/PR/Revision | 历史 Revision 与状态读取 |
| Impact Analysis/Risk/Path | 稳定 Cursor 排序 |
| Embedding Profile Snapshot/Status | 当前/历史 Profile 状态 |
| Chunk Vector Profile/Snapshot/Chunk | 固定语义空间内的 Exact Search 与 Batch 幂等 |

查询必须先限制 Snapshot 或 Repository，再使用文本索引，不能在所有 Workspace 和历史 Snapshot
上进行无界扫描。

## 8. 内容寻址与增量复用

Scanner 对原始字节计算 `sha256:<hex>`。`content_blobs.hash` 是主键，相同内容跨 Snapshot
复用；`snapshot_files` 保留每个 Snapshot 的 Path、语言和行数。

增量索引还会从兼容基线还原 ParsedFile，但不会让新 Snapshot 引用基线 Symbol/Edge：

1. Worker 比较 Current 与 Base 的文件元数据。
2. 复用或重新生成 ParsedFile。
3. 对完整 ParsedFile Set 重新链接。
4. 完成事务插入当前 Snapshot 的完整 File/Symbol/Edge/Chunk。

因此删除基线不会破坏已经 Ready 的增量 Snapshot。`base_snapshot_id` 是 Provenance，不是运行时
依赖。

所有允许的文本当前内联在 PostgreSQL；没有 MinIO/S3。单文件默认限制 2 MiB、仓库总文本默认
限制 500 MiB，避免无界 Blob 增长。以后引入对象存储必须通过新 Migration 和 Adapter。

## 9. Code Chunk、透明搜索与 Embedding Profile

完成事务为每个文本文件保存 File Chunk；可解析文件另外保存 Symbol Chunks。大文件使用受限
字符窗口分块，既覆盖顶层代码、Markdown 和不支持的语法，又提供精确声明范围。

检索使用 `simple` 配置全文向量、Symbol/Path 模糊匹配和固定 Profile 内的 Cosine Similarity。

`snapshot_embedding_indexes` 的唯一键为 `(snapshot_id, provider, model, input_version)`。Profile
保存 `queued|running|ready|failed|cancelled`、可变 Dimension（1～16000）、Total/Embedded Count、
Revision 和对外安全 Failure。只有 `embedded_chunks=total_chunks` 且 Dimension 有效时才可 Ready。

`code_chunk_embeddings` 通过两组复合 FK 同时证明 Profile/Chunk 属于相同 Snapshot；Primary Key
为 `(embedding_index_id, code_chunk_id)`。每行保存 Content Hash、Input Hash、Dimension 和
`vector`，数据库用 `vector_dims` 再验证维度。Worker Resume 只复用 Hash 匹配行。

Semantic SQL 必须先固定 `embedding_index_id/snapshot_id/dimensions`，在 Profile 内按 Distance 排序
并限制候选，然后加载 File/Symbol/Commit Metadata。v0.4 不创建 HNSW/IVFFlat：不同 Profile 可
有不同 Dimension，当前单 Snapshot Corpus 有界，真实 Plan 先证明 Exact Search 可接受。

旧 `code_chunks.embedding vector(1536)`、`embedding_model` 和 Snapshot `embedding_model` 保留以便
读取旧数据，新代码不读写这些字段。

## 10. Workspace、分享和 Citation

初始 Migration 仍插入固定 Public User、Public Workspace 和 Owner Membership，用于匿名 Demo。
v0.5 起 API 同时支持 GitHub Session、Workspace 成员角色、Bearer Token、私有 Repository 与
Workspace-scoped Access Query。数据库没有启用 RLS，因此任何新增查询仍必须在 Store/API 层携带
Workspace 或经过资源 Access Check；不能把随机 ID 当作权限边界。

Share Slug 包含仓库名、短 Commit 和随机尾部。Share 创建和 Answer 保存都验证 Snapshot 属于
目标 Repository。v2 Story 使用 `report_type=architecture_story`、`content_version=2`，并把固定
Graph 生成的 Metrics/Map/Module/Reading/Evidence/Provenance JSON 保存下来；旧 v1 不迁移。
Citation 指向实际 Snapshot File 和可选 Symbol，并保存行范围、Quote 与 Evidence Hash。

## 11. Guardrails Profile 与 Verified Explanation

`guardrail_profiles` 以 `(workspace_id, profile_key, version)` 和 fingerprint 唯一；内容相同的最新
创建请求复用版本，内容变化才递增。Repository 的可变绑定只影响未来 Snapshot，Snapshot 保存的
Profile ID 是历史 provenance。

`guardrail_explanations` 使用复合外键 `(workspace_id, snapshot_id)`，并以
`(workspace_id, snapshot_id, finding_fingerprint, provider, model_name, prompt_version)` 唯一。
Store 使用 `INSERT ... ON CONFLICT DO NOTHING` 后读取胜出的记录，因此并发相同请求只产生一行。
表是 append-only：保存服务端固定的 Finding/Profile/Commit/parser/algorithm，以及经过 verifier
过滤的 Answer。原始模型响应、完整源码文件、Provider 密钥和客户端 Prompt 不入库；Citation
Quote 仅保留服务端选取、位置已校验且有长度上限的摘录。

v1.0 为每条解释增加服务端计算的 `subject_key`，格式为 `sha256:<64 hex>`。Migration 0008 从
`finding_json` 按六类既有 Guardrails 配对规则回填 v0.9 记录，再设置非空与格式约束。该键用于连接
不同 Snapshot 中的同一逻辑 Finding，但不是授权边界；历史查询仍同时限定 Workspace、Repository
和 Snapshot Access。索引
`(workspace_id, subject_key, created_at DESC, id DESC)` 支持稳定倒序 cursor 分页，同时间戳下由
UUID 打破平局。比较查询通过 Snapshot JOIN 同时限定 Workspace 与 Repository，不写入任何结果。

## 12. 删除、保留与迁移

多数 Repository 子资源使用 `ON DELETE CASCADE`。Blob 因跨 Snapshot 复用，不随单个 File
自动删除；清理孤立 Blob 需要显式维护任务。当前 API 不提供 Repository Delete、Retention 或
Webhook Delivery 清理 Endpoint。

任何未来删除功能都必须先定义：目标 Workspace、Snapshot/Share 保留、Blob 引用、Delivery
审计、备份和可恢复策略。

当前迁移顺序：

1. `0001_initial.sql`：基础业务、任务、证据和分享 Schema。
2. `0002_incremental_github.sql`：Repository 自动更新字段、Snapshot 基线/模式和 Delivery 表。
3. `0003_pr_impact.sql`：PR Analysis、双 Snapshot、Change/Impact/Path/Evidence 与 Revision。
4. `0004_semantic_retrieval.sql`：Embedding Profile、Chunk Vector 与 Embedding Job 约束。
5. `0005_private_repository_auth.sql`：User/Workspace/Session/API Token、GitHub Installation 与审计。
6. `0006_guardrail_profiles.sql`：不可变 Guardrail Profile、Repository 绑定与 Snapshot provenance。
7. `0007_guardrail_explanations.sql`：不可变已验证解释、并发幂等唯一键与复合归属约束。
8. `0008_guardrail_explanation_history.sql`：逻辑 Finding `subject_key` 回填、格式约束和历史索引。

空库应记录恰好这八条 Migration；重复运行不执行任何 SQL 文件。回滚采用前向修复 Migration，
不提供会自动丢数据的 Down Migration。
