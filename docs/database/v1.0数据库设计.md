# v1.0 数据库设计：Explanation Subject History

状态：已实现并验收（2026-08-25）

## 1. Migration `0008_guardrail_explanation_history.sql`

在 `guardrail_explanations` 增加：

- `subject_key text`：服务端确定性逻辑 Finding 身份。

迁移使用 `finding_json` 与 `rule_id` 按共享配对规则回填全部 v0.9 记录。哈希输入采用有边界的规范
JSON 字符串数组，避免 path、symbol 或 target 中的分隔符把两个不同 Finding 合并。随后设置
`NOT NULL` 和格式约束。迁移不改变 `finding_json`、`answer_json`、Citation、Provider 或任何
provenance。

## 2. 索引

新增历史查询索引：

```sql
(workspace_id, subject_key, created_at DESC, id DESC)
```

查询同时通过 `repository_snapshots.repository_id` 限定 Repository。`subject_key` 只负责匹配候选，
不能替代 Workspace/Repository 权限条件。

## 3. 写入不变量

- `subject_key` 不接受 API 客户端输入，由 Store 使用固定 Finding 计算。
- 创建解释时保存 `subject_key`；v0.9 的幂等唯一键保持不变。
- Explanation 表继续 append-only；历史和比较都是只读查询。
- `subject_key` 不包含 Snapshot ID、Fingerprint 或 severity；Finding fingerprint 仍保留为单 Snapshot
  精确身份和幂等键。

## 4. Cursor

历史 cursor 编码版本、`createdAt` 和 Explanation UUID。解码后必须验证：

- 长度和 base64url 字符集；
- 版本为当前版本；
- 时间为合法 ISO datetime；
- ID 为合法 RepoVista UUID。

SQL 使用 `(created_at, id) < (cursor.created_at, cursor.id)`，排序与 cursor 完全一致，避免相同时间戳
下的重复或遗漏。

## 5. 删除与保留

删除 Workspace、Repository 或 Snapshot 时沿现有外键级联删除解释。v1.0 不新增单条删除能力，也不
改变历史保留策略。
