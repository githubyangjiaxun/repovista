# v0.4 数据库设计

状态：已实现并验收（2026-08-20）
迁移：`0004_semantic_retrieval.sql`

## 1. 设计目标

- 让 v0.1-v0.3 的任何 Ready Snapshot 无需重建源码图即可添加语义索引。
- 一个 Snapshot 可以保留多个 Provider/Model/Input Version 的历史 Index，但查询只进入单一
  语义空间。
- Partial Batch 可在 Worker 崩溃后恢复，Ready 状态必须可由数据库行重新证明。
- Vector Dimension 可变，同时禁止在一个 Index 内混维度或跨 Snapshot 引用。
- 保持 PostgreSQL 为唯一持久依赖。

## 2. `snapshot_embedding_indexes`

| 列 | 类型 | 规则 |
|---|---|---|
| `id` | `uuid PK` | 应用生成 UUIDv7 |
| `snapshot_id` | `uuid FK` | `repository_snapshots ON DELETE CASCADE` |
| `workspace_id` | `uuid FK` | 用于 Job 边界与未来授权 |
| `provider` | `text` | `ollama | openai-compatible` |
| `model` | `text` | 非空，最大长度由 API 限制 |
| `input_version` | `text` | v0.4 为 `code-chunk-v1` |
| `status` | `text` | `queued | running | ready | failed | cancelled` |
| `dimensions` | `integer null` | `1..16000`，首批成功后确定 |
| `total_chunks` | `integer` | 创建时固定，非负 |
| `embedded_chunks` | `integer` | 非负且不超过 total |
| `revision` | `integer` | 失败显式重试递增 |
| `error_code/message/retryable` | nullable | 稳定失败信息 |
| 时间列 | `timestamptz` | created/updated/started/ready/failed |

约束与索引：

```text
UNIQUE(snapshot_id, provider, model, input_version)
UNIQUE(id, snapshot_id)
CHECK(embedded_chunks <= total_chunks)
CHECK(status <> 'ready' OR dimensions IS NOT NULL)
CHECK(status <> 'ready' OR embedded_chunks = total_chunks)
INDEX(snapshot_id, created_at DESC)
INDEX(status, updated_at)
```

Profile 不保存 Endpoint 或 Secret。Model 是事实来源，不能只依赖当前环境变量。

## 3. `code_chunk_embeddings`

| 列 | 类型 | 规则 |
|---|---|---|
| `embedding_index_id` | `uuid` | Profile FK，联合主键一部分 |
| `snapshot_id` | `uuid` | 与 Profile/Chunk 的复合 FK 共同约束 |
| `code_chunk_id` | `uuid` | Code Chunk FK，联合主键一部分 |
| `content_hash` | `text` | 必须等于 Chunk 内容 Hash |
| `input_hash` | `text` | 最终 Embedding Input 的 SHA-256 |
| `dimensions` | `integer` | 与 `vector_dims(embedding)` 相同 |
| `embedding` | `vector` | 无固定 typmod；单 Profile 内一致 |
| `created_at` | `timestamptz` | 批次写入时间 |

约束：

```text
PRIMARY KEY(embedding_index_id, code_chunk_id)
FOREIGN KEY(embedding_index_id, snapshot_id)
  REFERENCES snapshot_embedding_indexes(id, snapshot_id) ON DELETE CASCADE
FOREIGN KEY(code_chunk_id, snapshot_id)
  REFERENCES code_chunks(id, snapshot_id) ON DELETE CASCADE
CHECK(dimensions BETWEEN 1 AND 16000)
CHECK(vector_dims(embedding) = dimensions)
```

为复合 FK 增加 `UNIQUE(code_chunks.id, code_chunks.snapshot_id)`。查询索引：

- `(embedding_index_id, code_chunk_id)` 主键用于缺失 Batch 与幂等。
- `(embedding_index_id, snapshot_id)` 用于范围过滤。
- v0.4 不创建 HNSW/IVFFlat，因为 `vector` 未固定维度且一个 Profile 的仓库规模有界。

旧 `code_chunks.embedding vector(1536)` 与 `embedding_model` 保留兼容但标记 Deprecated；新代码
不得读写它们。

## 4. `analysis_jobs` 增量

新增：

```text
embedding_index_id uuid NULL
  REFERENCES snapshot_embedding_indexes(id) ON DELETE CASCADE
```

并增加：

```text
UNIQUE(embedding_index_id) WHERE embedding_index_id IS NOT NULL
```

`job_type='embed_snapshot'` 时必须拥有 repository/snapshot/embedding_index；创建事务校验归属。
失败重试复用同一 Job 行并清理 Lease/Error/Finished 字段，`revision` 记录用户级重试次数，
`attempt_count` 记录 Worker 尝试。

## 5. 创建事务

`createOrRetryEmbeddingIndex` 在一个事务中：

1. `SELECT ... FOR UPDATE` Ready Snapshot、Repository 和 Workspace。
2. 统计 Snapshot Code Chunk；零 Chunk 仍可创建并立即 Ready，Dimensions 保持 null，Semantic
   查询返回无结果而不是错误。
3. 按唯一键查 Profile：
   - 无：插入 Profile + Job + queued Event；
   - queued/running/ready：返回现有资源；
   - failed/cancelled：Profile 重置 queued、revision+1，Job 重置 queued、attempt_count=0，保留
     匹配的 Partial Vector。
4. 返回 `profileId/jobId/status/reused`。

并发两个 POST 通过唯一键与行锁收敛为同一 Profile/Job。

## 6. Batch 查询与写入

### 读取下一批

```sql
SELECT chunk + file.path + symbol.name
FROM code_chunks chunk
JOIN snapshot_files file ...
LEFT JOIN symbols symbol ...
LEFT JOIN code_chunk_embeddings vector
  ON vector.embedding_index_id = $profile
 AND vector.code_chunk_id = chunk.id
WHERE chunk.snapshot_id = $snapshot
  AND (
    vector.code_chunk_id IS NULL
    OR vector.content_hash <> chunk.content_hash
  )
ORDER BY chunk.id
LIMIT $batch;
```

不能用 OFFSET；Partial Resume 依赖“缺失或过期”条件。

### 写入 Batch

- 事务第一步验证 Job status/lease owner/lease expiry。
- 首批用 `UPDATE ... WHERE dimensions IS NULL` 设置 Profile Dimension；并发/后续批次再次读取。
- 每行先验证 snapshot/content hash，再 Insert。
- Conflict 仅在 `content_hash` 与 `input_hash` 一致时视为幂等；否则抛
  `EMBEDDING_INPUT_STALE`。
- `embedded_chunks` 用数据库 Count 或本批增量加冲突保护更新，不能相信 Provider 返回数量。
- Event 只保存计数、Provider/Model、Dimensions 和耗时，不保存 Vector/源码/Secret。

## 7. Ready 完成事务

Worker 认为没有缺失 Batch 后，数据库重新执行：

```text
expected = count(code_chunks for snapshot)
actual = count(valid embedding rows for index joined to matching chunks)
dimensions = count(distinct dimensions)
```

只有 `actual=expected` 且 `dimensions<=1` 才能：

- Profile → ready、embedded=total、ready_at；
- Job → succeeded、progress=1、lease cleared、finished_at；
- 写 completed Event。

任何不一致整体回滚。

## 8. Semantic 查询

参数包含 Profile ID、Snapshot ID、Query Vector String、Dimensions 和 Limit：

```sql
SELECT ..., 1 - (e.embedding <=> $query::vector) AS score
FROM code_chunk_embeddings e
JOIN code_chunks c ...
JOIN snapshot_embedding_indexes i ...
WHERE e.embedding_index_id = $profile
  AND e.snapshot_id = $snapshot
  AND i.status = 'ready'
  AND i.dimensions = $dimensions
  AND e.dimensions = $dimensions
  AND e.content_hash = c.content_hash
ORDER BY e.embedding <=> $query::vector, file.path, c.start_line, c.id
LIMIT $limit;
```

API 在查询前验证 Vector；SQL 仍保留 Dimension/Status/Hash 防御。
