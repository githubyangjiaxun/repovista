# 数据库迁移与查询规范

状态：proposal

## 1. Migration 原则

- 所有结构变化必须通过版本化 Migration。
- Migration 一旦进入主分支不能修改，只能新增修复 Migration。
- 应用启动不自动执行生产 Migration。
- 生产迁移由独立命令执行并记录版本。
- 每个 Migration 都要说明向前执行、兼容窗口和回滚策略。

## 2. Expand and Contract

破坏性字段变更拆成多次发布：

1. Expand：新增可空字段或新表。
2. Deploy：应用同时写旧字段和新字段。
3. Backfill：分批补数据。
4. Verify：对比新旧数据。
5. Switch Read：切换读取来源。
6. Contract：后续版本移除旧字段。

不要在一个 Migration 中直接重命名高频字段并立即发布只认识新字段的应用。

## 3. 大表变更

- 创建普通索引时评估 CONCURRENTLY。
- 添加非空字段先允许 NULL、回填、再加约束。
- 大批回填按主键区间分批，并限制速率。
- 避免长事务。
- 约束可先 NOT VALID，再验证。
- Migration 设置 statement_timeout 和 lock_timeout。

示例：

~~~sql
SET lock_timeout = '2s';
SET statement_timeout = '30s';

ALTER TABLE messages
    ADD COLUMN answer_status text;

ALTER TABLE messages
    ADD CONSTRAINT messages_answer_status_check
    CHECK (answer_status IN ('grounded', 'partial', 'refused'))
    NOT VALID;

ALTER TABLE messages
    VALIDATE CONSTRAINT messages_answer_status_check;
~~~

## 4. 事务边界

应该在同一事务：

- 创建 Repository、Snapshot 和初始 Job。
- 更新 Job 终态与 Snapshot 终态。
- 保存完整 AI 消息和已验证引用。
- 撤销分享页并写审计记录。

不应该放在数据库事务内：

- Git clone。
- Tree-sitter 批量解析。
- 外部模型调用。
- 对象存储大文件上传。

长操作采用状态机和补偿，不保持数据库连接等待外部服务。

## 5. 查询规范

- 业务查询必须显式带 workspace_id 或通过 RLS。
- 禁止 SELECT *。
- 列表使用 cursor pagination，不使用深 OFFSET。
- 批量查询避免 N+1。
- 图遍历设置最大深度和最大节点数。
- 所有 LIKE 模糊搜索评估 trigram 索引。
- 向量查询必须先按 snapshot_id 过滤。
- JSONB 仅在明确索引和查询路径时使用。

## 6. Cursor 分页

按 created_at + id 稳定排序：

~~~sql
SELECT id, status, requested_at
FROM repository_snapshots
WHERE repository_id = $1
  AND (requested_at, id) < ($2, $3)
ORDER BY requested_at DESC, id DESC
LIMIT $4;
~~~

Cursor 对用户应编码为不透明字符串，不能依赖客户端拼 SQL 条件。

## 7. 任务领取查询

~~~sql
WITH candidate AS (
    SELECT id
    FROM analysis_jobs
    WHERE
        status = 'queued'
        OR (
            status = 'running'
            AND lease_expires_at < now()
        )
    ORDER BY priority ASC, created_at ASC
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE analysis_jobs AS jobs
SET
    status = 'running',
    lease_owner = $1,
    lease_expires_at = now() + interval '30 seconds',
    attempt_count = attempt_count + 1,
    started_at = COALESCE(started_at, now())
FROM candidate
WHERE jobs.id = candidate.id
RETURNING jobs.*;
~~~

Worker 只有持有正确 lease_owner 时才能完成任务。

## 8. 图查询边界

递归 CTE 必须有：

- depth 上限。
- visited 防环。
- 节点总数上限。
- snapshot_id 条件。
- 关系类型白名单。

不要允许客户端传任意 SQL 或无限深度。

## 9. 全文与向量混合检索

第一版使用 Reciprocal Rank Fusion：

1. 全文查询取前 N 条。
2. 向量查询取前 N 条。
3. 符号精确匹配取前 N 条。
4. 按来源排名融合。
5. 按 content_hash 去重。
6. 进行图邻接扩展。

所有结果必须保留 snapshot_file_id、start_line 和 end_line，无法定位的结果不能进入模型上下文。

## 10. 性能审查

新查询进入主分支前：

- 在接近真实规模的数据上运行 EXPLAIN ANALYZE。
- 记录 p50 和 p95。
- 检查是否出现顺序扫描、大量临时文件或错误估算。
- 检查索引大小和写入成本。
- 验证 workspace 和 snapshot 过滤足够早。

慢查询阈值建议从 500ms 起步，后续按接口目标细化。

## 11. 备份与恢复

- 云端数据库启用自动备份和 PITR。
- 定期进行恢复演练，不只检查备份任务成功。
- 对象存储版本和数据库快照保持一致的保留策略。
- 本地模式提供 pg_dump 导出命令。
- 密钥和 Token 不进入普通业务备份的明文。

## 12. 数据库测试

- Migration 从空库可以完整执行。
- Migration 可以从上一个发布版本升级。
- Repository 约束测试。
- RLS 越权测试。
- Job 并发领取测试。
- 幂等写入测试。
- Blob GC 不删除仍被引用内容。
- 混合检索结果固定数据集回归。
