# 迁移与查询规范

状态：v0.2 已实现并通过真实 PostgreSQL 验收（2026-08-20）

## 1. Migration 机制

SQL 文件位于 `packages/database/migrations`，按文件名排序。`migrateDatabase`：

1. 确保 `schema_migrations` 存在。
2. 读取已应用 Version。
3. 对每个新 SQL 文件开启事务。
4. 执行 SQL 并写入文件名。
5. 任一步失败即 Rollback。

当前 Migration：

1. `0001_initial.sql`：基础业务、任务、证据和分享 Schema。
2. `0002_incremental_github.sql`：增量 Snapshot、Repository 自动更新和 Webhook Delivery。

## 2. 命令

本地默认数据库：

```bash
docker compose up -d postgres
pnpm db:migrate
pnpm db:seed
```

Compose 中 API 设置 `RUN_MIGRATIONS_ON_START=true`，容器启动时自动执行；Worker 设置 false，避免并发重复工作。Migration 本身仍通过 `schema_migrations` 保持幂等。

## 3. 新增 Migration

- 使用下一个递增前缀，例如 `0003_add_repository_retention.sql`。
- 只向前新增，不重写已经合并或发布的文件。
- 尽量让 DDL 和回填可在一个事务内完成。
- 大表回填应拆成兼容 Schema、分批回填、切换读取、最后约束。
- 添加非空列时先提供 Default/Nullable 过渡，避免旧进程立即失败。
- 索引名称必须表达表、列和用途。
- 破坏性变化需要在 CHANGELOG 和发布说明中明确升级路径。

当前没有自动 Down Migration。回滚应用版本时数据库必须保持向后兼容，或提供经过审阅的
独立恢复 SQL/备份方案。

## 4. 查询规则

- 所有动态值使用 `$1` 等参数，不进行字符串拼接。
- 业务查询必须通过 `RepoVistaStore`，Migration/Health 除外。
- Source、Graph、Search 必须显式限制 `snapshot_id`。
- Repository 读取限制 Public Workspace 或明确 ID。
- 列表必须有稳定排序；Cursor 与同一排序键匹配。
- 写入 Ready Snapshot、Latest Pointer 和 Job Terminal State 必须同事务。
- Claim/Complete 必须锁定 Job 并验证 Lease Owner。
- 不在事务中执行网络、Clone、Parser 或模型请求。

## 5. 事务边界

适合单事务：

- 创建 Repository/Snapshot/Job/Event。
- 幂等处理 GitHub Delivery，并创建 Repository/Snapshot/Job/Event。
- 完成索引全部实体与终态。
- 失败/取消 Job 与对应 Snapshot Event。
- 保存 Conversation、Messages 和 Citations。
- 创建 Share Report。

不适合长事务：

- Git Clone。
- 文件扫描和 Tree-sitter。
- 模型生成。
- 等待 SSE 客户端。

长工作通过 Job 状态机衔接，每个 DB 事务保持短小。

## 6. 全文与图查询

全文查询先过滤 `code_chunks.snapshot_id`，再使用 `search_vector` 或 Path/Symbol trigram，最后限制条数。返回 Evidence 必须包括 File、Commit、Source Range、Content 和 Hash。

图查询批量读取 Snapshot Files、Symbols、Edges，在应用层构建 package/file/symbol 视图。避免每个节点单独 SQL 的 N+1。

## 7. 集成测试

数据库测试只有设置 `DATABASE_TEST_URL` 才运行：

```bash
DATABASE_TEST_URL=postgresql://repovista:repovista@127.0.0.1:5432/repovista_test \
pnpm --filter @repovista/database test
```

测试会执行真实 Migration，并验证：

- 创建和 Claim Job。
- 完整 Snapshot 持久化。
- 图、源码、文件列表和搜索。
- 答案与 Citation 保存。
- Share Report 创建和读取。
- 兼容增量基线选择、ParsedFile 还原和完整增量完成事务。
- Webhook Delivery 幂等、Payload 冲突和 Repository Automation Metadata。
- 测试 Repository 清理及孤立 Blob 清理。

`pnpm test` 在没有 URL 时会明确 Skip 该文件；发布结论不能把 Skip 当作 PostgreSQL 已验证。CI 提供 pgvector PostgreSQL Service 和 `DATABASE_TEST_URL`。

## 8. Schema 审阅清单

- [ ] 新列是否需要默认值或回填？
- [ ] 唯一约束是否符合重试幂等性？
- [ ] 外键 Delete 行为是否会误删共享数据？
- [ ] 查询是否有 Snapshot/Workspace 范围？
- [ ] 热路径是否有可验证的索引？
- [ ] Migration 是否能在空库和已有库执行？
- [ ] 旧应用是否能在 Migration 后短暂运行？
- [ ] 集成测试是否真正连接 PostgreSQL？
- [ ] 文档、OpenAPI 或 Contract 是否受影响？

## 9. 生产要求

Compose 是单机开发/演示基线，不提供自动备份、PITR、连接代理或 HA。生产部署必须由运营环境提供备份、恢复演练、磁盘监控、连接上限和加密传输。文档不得把这些外部要求描述为仓库已经实现的能力。
