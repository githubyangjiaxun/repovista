# v0.2 数据库设计

状态：已实现并通过真实 PostgreSQL 集成测试（2026-08-20）
迁移：`0002_incremental_github.sql` 已新增并执行；绝不重写已发布的
`0001_initial.sql`。

## 1. Repository 扩展

`repositories` 新增：

| 字段 | 类型 | 约束 | 用途 |
|---|---|---|---|
| `auto_update_enabled` | boolean | NOT NULL DEFAULT false | 是否已由有效 GitHub Push 启用自动更新 |
| `github_installation_id` | bigint | nullable, positive check | Payload 中的 Installation ID，仅作来源记录 |
| `last_webhook_at` | timestamptz | nullable | 最近一次有效且属于此仓库的 Push 时间 |

现有 `provider_repo_id` 保存 GitHub Repository Numeric ID。v0.2 不保存 Installation Token、PAT 或 Webhook Secret。

Repository Summary 从这些字段映射 Automation 状态；不能用“存在任意 Delivery”做每次请求的昂贵聚合。

## 2. Snapshot 扩展

`repository_snapshots` 新增：

| 字段 | 类型 | 约束 | 用途 |
|---|---|---|---|
| `base_snapshot_id` | uuid | FK self, ON DELETE SET NULL | 实际复用解析结果的兼容基线 |
| `index_mode` | text | NOT NULL, `full/incremental` | 本次索引模式 |

继续使用已有 `tree_hash`；Ready v0.2 Snapshot 必须非空。已有 `parent_commit_sha` 保留 Git Commit Parent 的语义，不能拿它冒充增量基线 Commit。

`stats_json.indexing` 保存可展示的计数：

```json
{
  "mode": "incremental",
  "baseSnapshotId": "uuid",
  "baseCommitSha": "40-char sha",
  "scannedFiles": 120,
  "changedFiles": 4,
  "reusedFiles": 88,
  "parsedFiles": 3,
  "deletedFiles": 1
}
```

计数属于 Snapshot 生成事实，和 Snapshot 一起不可变。数据库 Check 只负责结构列的强约束；JSON 结构由共享 Zod Contract、Store 写入和集成测试共同约束。

索引：

```text
(repository_id, parser_version, ready_at DESC)
WHERE status = 'ready'
```

用于基线选择。

## 3. GitHub Delivery 表

新增 `github_webhook_deliveries`：

| 字段 | 类型 | 约束 |
|---|---|---|
| `delivery_id` | text | PRIMARY KEY，非空且长度受限 |
| `event_name` | text | NOT NULL |
| `payload_sha256` | text | NOT NULL，格式 `sha256:<64 hex>` |
| `status` | text | `enqueued/ignored` |
| `reason` | text | nullable |
| `repository_id` | uuid | nullable FK, ON DELETE SET NULL |
| `snapshot_id` | uuid | nullable FK, ON DELETE SET NULL |
| `job_id` | uuid | nullable FK, ON DELETE SET NULL |
| `received_at` | timestamptz | NOT NULL DEFAULT now() |
| `processed_at` | timestamptz | NOT NULL DEFAULT now() |

不保存原始 Payload，减少无必要的外部数据留存。`payload_sha256` 用于判断同一 Delivery ID 是否被异常地配上不同 Body；遇到 Hash 不同必须返回冲突错误，不能把它当正常重放。

## 4. 事务不变量

### Webhook 入队

一次事务内完成：

1. Insert Delivery；冲突时读取既有结果。
2. Upsert Repository Identity 与 Automation Metadata。
3. Insert requested Snapshot。
4. Insert queued Job，`idempotency_key = github:<delivery_id>`。
5. Insert Job queued Event。
6. Update Delivery 为 enqueued 并关联三者。

任一步失败全部回滚，因此不存在“Delivery 已成功但 Job 丢失”的半状态。

### 完成增量 Snapshot

一次事务内完成：

1. `FOR UPDATE` 验证 Job Lease Ownership。
2. 写入 Snapshot Commit、Tree Hash、Base Snapshot、Mode。
3. 写入完整 File/Symbol/Edge/Chunk 集合。
4. Snapshot 变 Ready。
5. Repository Latest Pointer 更新到当前 Snapshot。
6. Job 变 Succeeded 并追加 completed Event。

## 5. 兼容与回滚

- Migration 为旧 Repository 填充 `auto_update_enabled=false`。
- 旧 Snapshot 填充 `index_mode=full`、`base_snapshot_id=null`，`tree_hash` 可以继续为空。
- API 对旧 `stats_json` 映射 `indexing=null`。
- Migration 必须幂等地由现有 Runner 执行一次；回滚采用前向修复 Migration，不提供会丢数据的自动 Down。
- Delivery 表可以按未来运维策略清理，但 v0.2 不自动删除审计记录。

## 6. 数据库测试

- 旧库执行 0002 后数据可读，重复 Migration 无变化。
- 基线查询不会选择 Failed、不同 Parser Version 或当前 Snapshot。
- 同 Delivery 并发两次只生成一个 Snapshot/Job。
- 同 Delivery + 不同 Payload Hash 返回冲突。
- 增量完成后 Latest Pointer、Base FK、Mode、Tree Hash 和 Stats 同步提交。
- Lease Lost 时上述任何完成数据都不可见。
- 删除 Repository 后 Delivery 审计仍保留，但 Repository/Snapshot/Job FK 置空。

## 7. 实现结果

- `0002_incremental_github.sql` 已在真实 PostgreSQL 17 + pgvector 上由 Migration Runner 执行。
- Store 集成测试覆盖增量基线/完成事务、Webhook 幂等与 Automation Metadata，共 3 项通过。
- Compose 空库启动自动执行 `0001_initial.sql` 和 `0002_incremental_github.sql`；已有库再次启动不会重复执行。
