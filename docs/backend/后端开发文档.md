# 后端开发文档

状态：v0.4 已实现并验收（2026-08-20）

## 1. 服务边界

后端由两个独立进程组成：

- `apps/api`：Fastify，同步 HTTP、SSE、Webhook、透明检索、Chat/Embedding 调用、Impact、Story
  和导出。
- `apps/worker`：PostgreSQL Job Loop，执行 Clone、扫描、增量计划、解析、建图、持久化和可恢复
  Embedding Batch。

长任务不能放进 API Request。两个进程只通过 PostgreSQL 状态协作，没有内存队列或 Redis。
Webhook 只做验签、筛选和任务入队；Markdown/SVG、Search 和 Story Builder 都是对 Ready
Snapshot/Ready Profile 的有界同步读取。

## 2. API 结构

```text
apps/api/src/
├── server.ts   配置、可选 Migration、监听端口
├── app.ts      Fastify、CORS、限流、原始 Body、错误处理、Health
├── retrieval.ts  四通道检索、Provider、降级与 Trace 编排
└── routes.ts     v1 路由和 Use Case 编排
```

共享实现位于：

```text
packages/config     环境变量 Zod Schema
packages/contracts  HTTP 数据结构和 Parser Version
packages/database   Store、Pool、Migration
packages/domain     DomainError 与领域类型
packages/git        GitHub URL、安全 Clone/Scan
packages/parser     TS/JS/Python/Go Tree-sitter Adapter
packages/graph      跨文件关系与多级图
packages/embeddings Ollama/OpenAI-compatible 协议、输入与 Vector 校验
packages/retrieval  Channel、Query Token 与稳定 RRF
packages/story      Architecture Story v2 纯函数
packages/ai         Provider 与 Answer Verification
packages/exporter   确定性 Markdown/SVG
```

API 不应为了读取 Parser Version 加载原生 Tree-sitter Binding；组合版本常量位于
`packages/contracts`，Parser Package 只重新导出给 Worker。

## 3. 请求处理顺序

普通 JSON 请求：

1. Fastify 分配或接收 Request ID。
2. CORS 与适用的 Rate Limit 执行。
3. Route 使用 Zod 解析 Params、Query 和 Body。
4. Ref、URL 和仓库路径执行额外安全校验。
5. Store 读取或写入 PostgreSQL。
6. 返回统一成功信封，或由全局 Error Handler 返回失败信封。

GitHub Webhook 必须使用不同顺序：

1. 限制 Body 大小并保留原始 Bytes。
2. 校验 Delivery/Event/Signature Header。
3. 对原始 Bytes 计算 HMAC-SHA256，并恒定时间比较。
4. 签名通过后才解析 JSON。
5. 校验 Repository Identity、完整 `after` SHA、Public/Default Branch/Deleted 条件。
6. Store 在单事务中处理 Delivery 幂等和任务入队。

不要在 Route 中直接拼 SQL；数据库行为进入 `RepoVistaStore`。不要让 Store 返回 Fastify
Reply、HTTP Status 或 Header。

## 4. 响应、附件和错误

普通成功响应：

```json
{
  "data": {},
  "meta": { "requestId": "request-id" }
}
```

失败响应：

```json
{
  "error": {
    "code": "SNAPSHOT_NOT_READY",
    "message": "The requested snapshot is not ready yet.",
    "retryable": true,
    "requestId": "request-id"
  }
}
```

明确的非信封成功响应：

- `/v1/health/live`、`/v1/health/ready` 返回 `{status}`。
- Job Events 返回 `text/event-stream`。
- Markdown/SVG Export 返回附件正文。

Export 仍必须设置 `X-Request-ID`、安全 `Content-Disposition`、`ETag`、
`X-Content-Type-Options: nosniff`；SVG 额外设置 Sandbox CSP。

`DomainError` 保存稳定 Code、Message、Details 和 Retryable。Zod 失败转换为
`VALIDATION_FAILED`。未知异常返回通用服务端错误，不能泄露 SQL、Secret、源码或临时路径。

## 5. Request ID、CORS 与限流

- 所有响应返回 `X-Request-ID`。
- Browser Origin 由 `WEB_ORIGIN` 控制。
- API 允许浏览器所需的 `Content-Type`、`X-Request-ID`、`Last-Event-ID` 等 Header。
- 匿名导入、问答和分享创建分别使用每小时配置上限。
- 列表、读取、Health、Integration Status、Export 和 Share 读取不计入上述业务限额。

当前没有身份认证。`users/workspaces` 是数据库演进边界，不是已启用的 HTTP 权限系统。

## 7. 数据库访问

`RepoVistaStore` 负责：

- 创建 Repository/Snapshot/Job。
- Claim/Renew/Fail/Cancel/Complete Job。
- 选择兼容增量基线并还原 ParsedFile。
- 写入和读取 Snapshot 图、源码、文件、检索证据。
- 创建/重试 Embedding Profile/Job，读取缺失 Chunk Batch，原子保存 Vector/Progress 并证明 Ready。
- 执行 Text、Symbol 和固定 Profile 内的 Semantic Candidate Query。
- 创建/读取 PR Analysis、Impact、Path、Evidence 与 Revision。
- 保存问题、验证后答案和 Citation。
- 创建和读取 v1/v2 Share Report。
- 幂等处理 GitHub Delivery，并更新 Repository Automation Metadata。

完成索引和 Webhook 入队分别使用独立事务。所有动态值使用参数化 SQL。列表使用稳定排序和
Cursor；Source 查询同时过滤 Snapshot 和 Path。

API 生成 Export 时只调用 Store 的只读方法。Exporter 不直接访问 Store，从而保持生成逻辑可
单元测试、可确定性重放。

## 8. 增量索引后端契约

Worker 从 Store 读取同 Repository、同 Parser Version、最近 Ready 且不是当前 Snapshot 的
基线。Planner 依据 Path、Content Hash、Language 和 Parse Status 决定：

- Full：没有兼容基线。
- Reuse：内容/语言不变，且基线解析成功。
- Parse：新增、内容或语言变化，或基线解析失败。
- Deleted：基线路径在当前扫描中不存在。

复用数据只是 Worker 构建新结果的输入。完成事务仍写入完整 Snapshot-local
File/Symbol/Edge/Chunk，并持久化 `baseSnapshotId/indexMode/treeHash/stats.indexing`。

## 9. Embedding Job

`POST /snapshots/:snapshotId/embeddings` 只创建或复用 Job，不在 API Request 内生成全库 Vector。
Worker 的 `embed_snapshot` Loop：

1. Claim Lease，并验证 Job Provider/Model/Input Version 与当前配置一致。
2. 按 Chunk ID 读取缺失或 Content Hash 过期的 Batch，不使用 OFFSET。
3. 构造受限 `code-chunk-v1` 输入，调用 Ollama `/api/embed` 或兼容 `/embeddings`。
4. 校验响应条数、有限数值、非零范数、最大 Dimension 和同 Profile 维度一致。
5. 在事务中验证 Lease/Hash、Upsert Vector、更新 embedded/total 与 Event。
6. 无缺失 Batch 后由数据库重新 Count；只有完整覆盖才标记 Profile Ready、Job Succeeded。

已验证 Partial Batch 在崩溃或可重试失败后复用。事务连接被 PostgreSQL 终止时，Store 监听已签出
连接 Error、安全 Rollback，并用 `release(error)` 淘汰坏连接，避免未监听事件终止 Worker。

## 10. 检索与问答编排

`retrieveEvidence` 接受 `text|symbol|semantic|hybrid`。每通道候选上限为
`min(200, max(20, limit * 4))`，并标记 Rank/Raw Score：

- Text 与 Symbol 直接查询 PostgreSQL。
- Semantic 选择当前配置的 Ready Profile、生成 Query Vector，再执行固定 Profile Exact Search。
- Hybrid 对可用通道做稳定 RRF；上游不可用时保留 Lexical，并返回明确 Degradation Reason。
- Semantic-only 不可用时返回 409/503，不静默切换模式。

单条 Evidence 在发给 Chat Provider 前限制约 8000 字符并重新计算内容哈希。Ask 复用同一
Hybrid Retriever 和 Trace，不再维护另一条隐藏检索路径。

Provider 只产生 Draft。`verifyModelAnswer`：

- 删除不存在的 Evidence ID。
- 删除没有合法 Evidence 的 Step。
- 从服务端 Evidence 重建 Citation。
- 无 Citation 时强制 Refused。
- 部分 Step 无证据时降级 Partial 并增加 Limitation。

配置 `MODEL_PROVIDER=none` 时问答路径使用透明的 `fake` Provider；静态功能从不依赖模型。

## 11. Webhook、PR Impact、Story 与导出

Webhook：

- `GET /v1/integrations/github` 只返回 enablement、Slug、事件和 Public Scope。
- `POST /v1/integrations/github/webhooks` 支持 `ping`、`push` 和安全忽略其他事件。
- 有效默认分支 Push 返回 202；Ping/Ignored/Duplicate 返回 200。
- 错签名返回 401；未配置返回 503；Delivery Body 冲突返回 409。

Export：

- `GET /v1/snapshots/:snapshotId/exports/markdown`。
- `GET /v1/snapshots/:snapshotId/exports/svg?level=package|file|symbol`。
- 只接受 Ready Snapshot；SVG 最多 250 个节点。
- 输出固定完整 Commit、Snapshot ID 和 Parser Version，不调用 AI。

PR Impact：

- GitHub Client 固定 Base/Head 完整 SHA并创建/复用 Snapshot。
- 影响算法使用确定性 bounded reverse BFS、风险分解、最短路径和固定 Evidence。
- 相同输入幂等；显式 rerun 创建下一 Revision。

Story：

- API 读取固定 Graph Data 并调用 `packages/story`。
- v2 包含 Metrics、Package Map、Key Modules、Reading Path、Evidence 与 Provenance。
- 创建后保存 JSON；公开读取不调用 Chat/Embedding Provider，旧 v1 Tour 继续可读。

## 12. OpenAPI 纪律

`openapi/openapi.json` 是机器可读 Contract。`scripts/validate-openapi.mjs` 启动应用、收集
Fastify Route，并比较 Method/Path 集合，当前应为 49 个 Operation。

新增或删除路由时必须同时：

1. 更新 Route。
2. 更新共享 Contract。
3. 更新 OpenAPI。
4. 增加行为测试。
5. 更新相关开发文档。
6. 运行 `pnpm openapi:check` 和 `pnpm check`。

文本或图片响应也必须在 OpenAPI 中准确声明，不能因为不使用 JSON 信封就漏掉。

## 13. 测试

- API Test 使用内存 Store Fake 和 Fastify Inject，不监听端口。
- Database Integration Test 在真实 PostgreSQL 上执行完整持久化、增量、Webhook、PR Impact、
  Profile/Vector、连接中断、三通道 SQL 和 v1/v2 分享。
- Parser/Graph/Worker Test 覆盖 Python/Go、增量计划、完整重新链接、租约、Edge 去重和 Embedding
  Batch 恢复。
- Embeddings/Retrieval/Story Test 覆盖协议异常、Vector 校验、RRF 稳定性和确定性 Story。
- Exporter Test 覆盖确定性、Provenance、XML 转义和节点上限。
- E2E 在浏览器网络层 Mock API，验证 UI Contract 和真实附件下载。
- 发布 Smoke Test 使用真实 API/Worker/PostgreSQL、容器和公共仓库。

单元测试通过不等于数据库、原生 Parser 或容器链路已经验证；发布审计必须运行对应层级的
证据。
