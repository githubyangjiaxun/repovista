# v1.2 后端开发文档：Reviewable Guardrails API

## 原则

Guardrail Report 是固定 Snapshot 上的纯确定性派生值。Review 是独立的 Workspace 元数据，
后端绝不能把 Review 字段传回规则引擎，也不能接受客户端提交的 severity、metric、message、
subjectKey 或 Snapshot provenance。

## API

### 列出当前审阅状态

`GET /v1/snapshots/{snapshotId}/guardrails/reviews`

- Viewer 和公开 Demo 可读；先执行 Snapshot access query。
- 服务端重新生成当前 Report，按 Report Finding 顺序返回每个 Finding 一项。
- 没有数据库记录的 Finding 返回 `status: unreviewed`、空备注和空审阅时间。
- 响应包含 `{ snapshot: { id, commitSha }, reviews: [...] }`。

### 设置审阅

`PUT /v1/snapshots/{snapshotId}/guardrails/reviews/{findingId}`

请求体：

```json
{"status":"accepted_risk","note":"Legacy boundary retained until the next refactor."}
```

`status` 可为 `acknowledged`、`accepted_risk`、`false_positive`；传 `unreviewed` 等价于清除当前
记录。备注会 trim，最长 2,000 个 Unicode 字符。写入者必须是 Session 的 owner/editor，或具备
`repo:write`/`workspace:admin` 的 Token；Session 必须通过 `Origin`、CSRF Cookie 和 Header 校验。

### 清除审阅

`DELETE /v1/snapshots/{snapshotId}/guardrails/reviews/{findingId}`

操作幂等，返回该 Finding 的 `unreviewed` 状态。清除也会记录审计事件（仅保存状态变化和长度，
不把备注原文写入审计元数据）。

## 安全和一致性

- Finding ID 必须精确匹配服务端当前 Report；不存在时返回稳定 `GUARDRAIL_FINDING_NOT_FOUND`。
- `subjectKey` 由 `guardrailFindingSubjectKey` 计算，只作一致性/展示辅助，不能替代授权条件。
- SQL 使用 `(workspace_id, snapshot_id, finding_id)` 唯一键和事务 upsert，避免并发重复记录。
- Bundled Demo 的 Review 写操作显式拒绝；公开读取仍可用。
- 私有 Snapshot 所有列表/写响应均 `private, no-store`。

## 错误码

`AUTH_REQUIRED`、`CSRF_INVALID`、`WORKSPACE_FORBIDDEN`、`SNAPSHOT_NOT_FOUND`、
`SNAPSHOT_NOT_READY`、`GUARDRAIL_FINDING_NOT_FOUND`、`GUARDRAIL_REVIEW_DEMO_READ_ONLY`、
`VALIDATION_FAILED`。

## 审计

Action 使用 `guardrail_review.upsert` 与 `guardrail_review.clear`，resource type 为
`guardrail_review`，resource id 为 Finding ID；metadata 包含 Snapshot、subject key、前后状态及
备注长度，不包含备注内容。
