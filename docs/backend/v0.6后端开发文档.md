# v0.6 后端开发文档：Architecture Guardrails

## 1. 设计原则

Guardrails 是 Snapshot 派生读模型，不新增数据库表。API 通过现有
`RepoVistaStore.getSnapshotGraphData(snapshotId)` 读取已经完成权限检查的不可变文件、符号和边，
交给 `@repovista/guardrails` 计算。这样可以保证报告不会混合不同 Commit，也不会在 Worker 尚未
完成索引时读取半成品。

## 2. API 边界

### `GET /v1/snapshots/:snapshotId/guardrails`

请求：路径中的 UUID；无请求体。

响应：标准 `{ data, meta }` Envelope，`data` 为 `GuardrailReport`。Snapshot 必须 `ready` 且有
完整 Commit SHA，否则返回 `SNAPSHOT_NOT_READY`。

### `GET /v1/snapshots/:snapshotId/guardrails/sarif`

响应头：

- `Content-Type: application/sarif+json; charset=utf-8`
- `Content-Disposition: attachment; filename="repovista-<snapshot>-guardrails.sarif"`
- 私有仓库：`Cache-Control: private, no-store`
- 公开仓库：`Cache-Control: public, max-age=0, must-revalidate`
- `X-Content-Type-Options: nosniff`

SARIF 只包含路径、行号、规则、摘要和 Snapshot URI，不嵌入源码全文、Cookie、Token 或 Secret。

## 3. 领域算法

`buildGuardrailReport` 接受：Snapshot、文件记录、符号记录和关系记录。计算步骤：

1. 建立 symbol/file/package 索引，丢弃不存在端点的关系。
2. 只用 `imports` 关系建立包图；用 Tarjan SCC 找环，保留长度 2–12 的强连通分量。
3. 对文件按行数和字节数检查 `large_file`。
4. 对非 module 符号按行跨度检查 `large_symbol`。
5. 统计非 `contains` 入边，检查 `high_fan_in`。
6. 对 `imports` 且没有 `toSymbolId` 的关系输出 `unresolved_import`，关系证据来自
   `evidence_json`。
7. 对 `parseStatus !== parsed` 的文件输出 `parse_failure`。
8. 生成稳定 fingerprint（规则 + Snapshot + 位置 + 关键指标），按 fingerprint 排序。

规则输出不读取网络、不调用模型、不依赖当前时间。`generatedAt` 使用 Snapshot 的
`readyAt ?? requestedAt`，因此相同输入报告稳定。

## 4. 安全与错误

- 路由先调用 `requireSnapshotAccess`，再调用 Store；跨 Workspace 不泄露报告是否存在。
- 只允许 `ready` Snapshot；避免对 `inline_content` 未完整持久化的数据生成结论。
- SARIF 文件名由 UUID 组成，不能由用户输入控制。
- 规则异常统一转为 `GUARDRAIL_ANALYSIS_FAILED`，不返回数据库 SQL 或源码。
- 结果中的 `path` 仍经过已有相对路径约束；不会拼接外部 URL。

## 5. 测试

- 纯函数：无环、单环、多环、同包边、超阈值、未解析导入、解析失败、稳定排序。
- API：ready/not-ready、public/private headers、跨 Workspace 404、SARIF 内容和无源码泄露。
- 与旧路由共用 Mock Store，确保不要求真实数据库迁移。
