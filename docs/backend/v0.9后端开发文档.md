# v0.9 后端开发文档：Verified Guardrail Explanations

## 1. API

### `POST /v1/snapshots/{snapshotId}/guardrails/explanations`

请求体严格为：

```json
{
  "findingId": "dependency_cycle:…",
  "provider": "fake",
  "model": "optional-model-name"
}
```

`provider` 可选值为 `fake`、`ollama`、`openai-compatible`；未知字段拒绝。`findingId` 必须来自服务端当前报告。

处理顺序：

1. 解析身份并检查 Snapshot 访问权限。
2. 要求 Snapshot 为 Ready，并确认路径中的 Snapshot 属于当前 Repository。
3. 使用 Snapshot 自身保存的 Profile 重新生成 Guardrails 报告，按精确 `findingId` 选择 Finding。
4. 根据 Finding evidence 的 path/range 从同一 Snapshot 读取源码；限制最多 20 个片段、每片最多 8,000 字符。
5. 以固定 prompt `guardrail-explanation-v1` 调用已配置 Provider，源码作为不可信数据。
6. 运行 citation verifier，仅保留 Evidence 中存在的 citation；固定 provenance 不由模型返回。
7. 通过事务和 `INSERT ... ON CONFLICT DO NOTHING` 写入不可变解释；唯一键命中时读取已有记录并标记 `reused=true`，并发请求不会生成重复数据库记录。

### `GET /v1/snapshots/{snapshotId}/guardrails/explanations/{explanationId}`

只返回该 Snapshot、当前身份 Workspace 可见的已持久化解释。响应带 `Cache-Control`：私有 Workspace 为 `private, no-store`，公开 Demo 要求重新验证。

## 2. 响应模型

响应包含：

- `id`、`createdAt`、`reused`；
- `snapshot`：Snapshot ID、Commit、parser、Guardrails algorithm；
- `profile`：创建该 Snapshot 时的完整 Profile（可兼容旧 `null`）；`profileFingerprint` 始终显式返回，旧 Snapshot 使用内置默认策略指纹；
- `finding`：服务端固定的 Finding ID、rule、severity、fingerprint、位置、metric；
- `answer`：经校验的 summary、steps、limitations、status、citations、provider、model；
- `promptVersion`。

客户端应把 `finding` 和 provenance 视为权威事实，把 `answer` 视为有引用的辅助说明。

## 3. 权限、限流与错误

- `requireSnapshotAccess` 负责 Workspace 隔离；匿名访问只适用于公开 Demo。
- 使用现有 AI 问答限流桶，避免为解释增加不可控供应商负载。
- `GUARDRAIL_FINDING_NOT_FOUND`、`GUARDRAIL_EXPLANATION_EVIDENCE_UNAVAILABLE`、`GUARDRAIL_EXPLANATION_NOT_FOUND` 使用稳定错误码。
- Provider 错误沿用 `AI_PROVIDER_FAILED` / `AI_OUTPUT_INVALID`；错误响应不包含源码或密钥。
- 不保存原始模型响应或完整源码文件；持久化答案只包含 verifier 接受的有界 citation 摘录。
- 不同 Snapshot、Profile 或 Finding fingerprint 不允许通过客户端字段绕过校验。
