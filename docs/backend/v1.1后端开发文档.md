# v1.1 后端开发文档：离线 Demo Seed Pipeline

状态：已完成验收（2026-08-27）

## 1. Fixture 构建

`@repovista/demo` 保存 Base/Head 两个真实目录树。加载器使用现有安全 Scanner 读取文本并计算
`contentHash`、语言、行数和字节数；稳定排序后的 path/content manifest 产生 40 位合成 revision。

Seeder 不执行 Fixture，不调用 Git，也不访问网络。Worker 的 clone/scan dependency 在这一条受控命令
中替换为固定 revision 和已扫描文件；Parser、Graph、Incremental Planner、Lease、进度事件与
`completeIndexJob` 均继续使用生产实现。

## 2. 精确 Job 领取

`RepoVistaStore.claimIndexJob` 增加可选 `jobId` 过滤。普通 Worker 不传该参数，行为不变；Seeder
必须传入 `createRepositoryImport` 返回的 ID。

SQL 仍要求 Job：

- `job_type = index_snapshot`；
- 为可用 queued，或 lease 已过期的 running；
- `attempt_count < max_attempts`；
- 使用 `FOR UPDATE SKIP LOCKED` 和原有租约字段。

精确 ID 不存在、尚不可领取或已被其他 Worker 持有时返回 `null`，Seeder 必须失败并保留现场，不能
转而领取其他任务。

## 3. Seed 编排

一次 Seed 顺序如下：

1. 执行 Forward Migrations。
2. 在 Public Workspace 中按保留 canonical URL 查找 Demo Repository。
3. 加载 Base/Head Fixture 和稳定 revisions。
4. 对缺失的 Base 创建 Import、精确 Claim、执行 Full Index。
5. 对缺失的 Head 重复流程；Incremental Planner 必须选择 Ready Base。
6. 重算两个 Snapshot 的 Guardrails，选择共同的 `dependency_cycle` Finding。
7. 从各自 Snapshot 读取有界源码证据，调用本地 `FakeModelProvider`，再使用现有 verifier。
8. 通过现有 Store 保存 Explanation；复合唯一键保证重复调用收敛。
9. 输出不含源码、模型响应或凭据的结果摘要。

若目标 Revision 已有兼容 Ready Snapshot，直接复用。Seeder 不删除失败记录、不覆盖用户 Repository、
不处理同 canonical URL 下未知的冲突数据。

## 4. Compose 生命周期

`demo-seed` 与 Worker 使用同一生产 Worker Image，但执行独立入口：

```text
PostgreSQL healthy -> API migrates/healthy -> demo-seed completes -> Worker starts -> Web healthy
```

`DEMO_SEED_ENABLED` 在通用配置中默认 `false`；本地 Compose 显式默认 `true`，Hardened Overlay 强制
`false`。这避免生产部署因升级而意外写入 Demo 数据。

## 5. 可信边界

- Fixture revision 是内容 manifest 的稳定摘要，不宣称是 GitHub 托管 Commit。
- Fake Provider 只证明 Evidence/Citation/History 管线，不证明外部模型质量。
- Seeder 不接受任意目录、URL、Prompt、Finding 或 Snapshot ID 参数。
- 现有匿名 Public Workspace 权限、缓存策略、API Contract 和 OpenAPI Operation 数不变。
