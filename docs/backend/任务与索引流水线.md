# 任务与索引流水线

状态：v0.2 已实现并验收

## 1. 为什么是 PostgreSQL 租约

v0.2 仍不引入 Redis。创建分析时 API 在同一数据库中写 Repository、Snapshot、Analysis Job 和初始 Event；Worker 使用原子 Claim 和租约协调。这样部署依赖少，状态与业务事务在一个事实源中。

## 2. Job 创建

`POST /v1/repositories` 完成：

1. 解析和 Canonicalize GitHub URL。
2. 校验 Allowed Host、Ref 和 Ignore Path。
3. 在 Public Workspace 创建或复用 Repository。
4. 创建 `requested` Snapshot。
5. 创建 `queued` 的 `index_snapshot` Job。
6. 写入 Job Event。
7. 返回 Repository/Snapshot/Job ID。

Job 的 Idempotency Key 由 Store 生成并有唯一约束，避免数据库重试产生重复 Job。

## 3. Claim 与租约

Worker Loop 每 `JOB_POLL_INTERVAL_MS` 尝试领取一条 Job：

- 新 `queued` Job。
- `running` 但租约已过期的 Job。
- 按 Priority 和 Created At 排序。
- Claim 后增加 Attempt Count，写 `lease_owner/expires_at`。

Worker 用独立 Heartbeat 续租。每个 Checkpoint 同时检查：

- 租约是否仍归当前 Worker。
- `cancel_requested_at` 是否已设置。
- Heartbeat 是否失败。

失去租约的 Worker返回 `lease-lost`，不能写终态。

## 4. 执行阶段

| 阶段 | Snapshot/Job 更新 | 主要工作 |
|---|---|---|
| cloning | 5% | 创建临时目录并浅克隆指定 Ref |
| scanning | 25% | 遍历安全文本文件，计算 Hash 和统计 |
| parsing | 45%～70% | 以 25 个文件一批运行 Tree-sitter |
| building_graph | 75% | 解析本地 Import 和 Symbol 关系 |
| persisting | 90% | 事务写 Blob/File/Symbol/Edge/Chunk |
| completed | 100% | Snapshot ready，Job succeeded |

当前解析 TypeScript、JavaScript 和 Python；其他已识别文本文件仍可作为源码和全文证据保存。

Clone/Scan 后 Worker 选择同 Repository、同 Parser Version 的最近 Ready Snapshot 作为兼容基线。Planner 按 `path + content_hash + language + parse_status` 决定重新解析或复用：

- 首次或没有兼容基线：Full。
- 内容/语言变化或新增的可解析文件：Parse。
- 内容未变且基线 Parse 成功：复用 ParsedFile。
- 基线存在但当前不存在：Deleted 计数。

复用与新解析结果合并后，完整 ParsedFile Set 重新执行 Import Linking。新 Snapshot 持久化完整 File/Symbol/Edge/Chunk，不需要查询时回溯基线拼接。

完成持久化时每个文本文件都会建立一个 File Chunk；可解析文件另外建立 Symbol Chunks。这样
文件级顶层代码、Markdown 和不支持语法解析的文本仍能被全文检索，同时符号检索保留更精确
的行范围。大文件按受限字符窗口分块，不会只保留文件开头。

## 5. Git 安全约束

Clone 使用参数数组而不是 Shell 字符串，并设置：

- `core.hooksPath=/dev/null`。
- `--depth 1 --no-tags --single-branch`。
- `GIT_TERMINAL_PROMPT=0`。
- `GIT_ALLOW_PROTOCOL=https`。
- `GIT_CONFIG_NOSYSTEM=1`。
- Clone 和 `rev-parse` 超时。

当 Ref 是完整 40 位 Commit SHA 时，Worker 使用 `git init`、添加远端、
`git fetch --depth 1 origin <sha>` 和 detached checkout；不会把 SHA 当作 Clone Branch。
完成后再次验证 HEAD 是 40 位 SHA。

API 只生成 GitHub HTTPS Clone URL，用户不能直接提供任意协议或命令参数。

## 6. Scanner 约束

- 默认忽略 `.git`、`node_modules`、`vendor`、`dist`、`build`、`.next`、`coverage`、`.turbo`。
- 额外应用用户传入的精确文件/目录前缀 Ignore。
- 跳过 `.env*`、`.pem`、`.key`。
- 遇到符号链接直接失败。
- 跳过单文件上限以上文件和包含 NUL 的二进制。
- 超过总文件数或总字节数时失败。
- 所有 Path 统一为 `/` 分隔的仓库相对路径。

## 7. Parser 和图

Tree-sitter 统一 Adapter 提取：

- 每个文件一个 Module Symbol。
- TypeScript/JavaScript 的 Function、Generator Function、Class、Abstract Class、Interface、Type Alias、Enum、Method。
- Python 的 Module、Function、Class、Method、模块级 Variable。
- `contains`、`imports`、`calls`、Python `extends` 边。
- Syntax Evidence 的文件和行范围。

本地相对 Import 会解析到目标文件 Module；无法解析的 Import/Call 保留
`unresolved_target`，不伪造目标 Symbol。外部包 Import 同样保留为 unresolved edge，不能
因为没有本地目标就静默删除。`.js`、`.jsx`、`.mjs` 和 `.cjs` 的相对 Import 会尝试回溯到
对应 `.ts`/`.tsx` Source；Python 相对模块和仓库内绝对模块会尝试解析到 `.py` 或 `__init__.py`。

## 8. 完成事务

完成索引时 Store 在一个事务中：

1. 锁定 Job 并验证 Lease Owner（失败和取消终态也必须匹配 Job、Snapshot、Worker 和 running
   状态）。
2. Upsert 内容寻址 Blob。
3. 插入 Snapshot Files。
4. 插入 Symbols 并建立 Stable Key 到 UUID 映射。
5. 插入解析后 Edges。
6. 为文件/符号建立 Code Chunks 和全文索引。
7. 更新 Snapshot Stats/Commit/Ref/Base Snapshot/Index Mode/Tree Hash/Ready At。
8. 更新 Repository Latest Ready Snapshot。
9. 更新 Job succeeded 并写 completed Event。

事务失败则不出现半 Ready Snapshot。

## 9. 失败、重试和取消

- Domain Error 保留 Code 和 Retryable。
- 非预期错误转换为 `INDEXING_FAILED`。
- Store 根据 Retryable、Attempt Count 和 Max Attempts 决定重新排队或终止失败。
- Cancel Endpoint 设置请求；Worker 在下一个 Checkpoint 标记 Job/Snapshot cancelled。
- 无论成功、失败、取消或丢租，Finally 都删除临时目录。
- Lease 丢失时 Worker 返回 `lease-lost`，不会覆盖另一 Worker 已写入的终态；重试 Claim 会
  清理旧错误和进度，Job API 的 `retryable` 与最终失败状态一致。

## 10. 可观测性

v0.2 的事实来源是：结构化 Fastify 日志、Worker 标准输出、Job 行和 Job Events。尚未接入 OpenTelemetry/Prometheus；文档不能声称已经具备 Trace 或 Metrics Backend。

排错顺序：Job API → Job Events → Worker Log → Snapshot Failure → PostgreSQL 行。用户报告问题时应提供 Request ID、Job ID 和 Snapshot ID，不需要发送完整源码。
