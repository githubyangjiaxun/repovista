# v0.7 后端开发文档：Guardrails Snapshot Baseline

状态：已实现并验收（2026-08-23）

## 1. 设计原则

比较是两个不可变 Snapshot 的派生读模型。API 读取两边的 Graph Data，分别调用 v0.6 的
`buildGuardrailReport`，再由 `compareGuardrailReports` 组合结果。不得复用 Repository 当前最新
指针，也不得把一个快照的 Finding 与另一个快照的源码混合。

## 2. 请求与校验

```http
GET /v1/snapshots/:headSnapshotId/guardrails/compare?baseSnapshotId=:baseSnapshotId
```

校验顺序：

1. 解析两个 UUID；缺少或非法参数返回 `VALIDATION_FAILED`。
2. 对 head、base 分别执行 `getSnapshotAccess`，无权或不存在统一返回 Snapshot Not Found。
3. 读取两个 Snapshot Graph Data；两者必须属于同一 Repository。
4. 两者必须 `ready`、Commit 非空、Parser Version 相同。
5. Guardrails algorithm 与阈值必须相同，否则返回 `GUARDRAIL_COMPARISON_INCOMPATIBLE`（409）。
6. 生成并返回比较结果。

不新增 Store 方法或 SQL Migration；现有 `getSnapshotGraphData` 已返回完整文件、符号、边和快照
元数据。若未来需要缓存，必须以两个 Snapshot ID、算法版本和阈值作为完整键。

## 3. 比较算法

`findingComparisonKey(finding)` 不包含 Snapshot ID：

- `dependency_cycle`：规则 + `metric.packages`。
- `large_file` / `parse_failure`：规则 + 路径。
- `large_symbol` / `high_fan_in`：规则 + 路径 + `metric.symbol`。
- `unresolved_import`：规则 + 路径 + 起始行 + `metric.target`。

同一键出现多次时按 Finding ID 排序并以序号配对，保证不丢结果。配对 Finding 完全相同为
`unchanged`；键相同但位置、级别、指标或消息变化为 `changed`。只在一侧出现分别为 `added` 或
`resolved`。

严重级别顺序为 `info < warning < error`。新增/升级 warning 或 error 计入 regression；解决/降级
warning 或 error 计入 improvement。若同时存在两者，整体状态为 `regressed`。

## 4. 响应安全

- JSON 只返回 Finding 的 bounded evidence，不返回 `content`、Blob 或凭据。
- 私有结果使用 `Cache-Control: private, no-store`；公开结果使用 `public, max-age=0,
  must-revalidate`。
- `baseSnapshotId` 不通过错误消息回显跨 Workspace 的资源存在性。
- 结果生成时间使用 head 报告的固定 `readyAt`，不使用当前墙上时间，便于重放。

## 5. 测试要求

覆盖纯函数稳定性、重复键、严重级别升降、跨仓库、跨 Workspace、非 Ready、Parser 不兼容、响应
无源码和缓存头。OpenAPI 必须与 Fastify 路由保持一一对应。
