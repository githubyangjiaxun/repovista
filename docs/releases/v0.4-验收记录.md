## 3. 检索质量与透明降级

五类自然语言查询人工核对了目标源码。不同措辞会改变模型排序，因此这里记录的是验收时的
观察，不把它描述成稳定模型基准：

| 意图 | 人工确认目标 | Semantic 观察 | Lexical 对照 |
|---|---|---|---|
| 响应压缩 | `middleware/compress.go` `Handler` | 第 2 | 多数无 Text/Symbol 命中 |
| 请求唯一 ID | `middleware/request_id.go` | 第 1/2 | 多数无 Text/Symbol 命中 |
| 路由遍历 | `tree.go` `walk` | 第 5 | 无目标命中 |
| Handler 超时 | `middleware/timeout.go` `Timeout` | 第 2 | 多数无 Text/Symbol 命中 |
| Panic 恢复 | `middleware/recoverer.go` `Recoverer` | 第 14 | 测试函数排第 1，暴露模型局限 |

后四类查询大多数 Text/Symbol 通道返回空集合，而 Semantic 找到了人工确认的源码，证明本版本
不是把全文结果重新贴上“AI”标签。Panic 场景同时证明真实 Embedding 会把测试代码或相邻概念
排在实现前面；RepoVista 公开 Rank/Score 和源码证据，不掩盖这一限制。

停止 Ollama 后实测：

- `mode=hybrid`：HTTP 200，Text/Symbol 结果继续返回，Trace 为
  `degraded=true`、`degradationReason=provider_unavailable`。
- `mode=semantic`：HTTP 503，稳定错误码 `EMBEDDING_UPSTREAM_UNAVAILABLE`，没有静默切换 Text。
- 重启 Ollama 后相同 Ready Profile 立即恢复查询，不需要重新嵌入。

仓库内 `pnpm benchmark` 另有一个 10 文档/5 查询的确定性 test-only Corpus，用于验证
Recall@1/3/5、MRR@10、候选数和 RRF 指标管线。该 Provider 明确叫
`deterministic-test-only-concept-v1`，不能作为真实模型效果宣传。

| Mode | Recall@1 | Recall@3 | Recall@5 | MRR@10 | 平均候选数 |
|---|---:|---:|---:|---:|---:|
| Text | 0.6 | 0.8 | 0.8 | 0.7 | 1.6 |
| Symbol | 0 | 0.4 | 0.4 | 0.1667 | 1.2 |
| Semantic | 1 | 1 | 1 | 1 | 1.8 |
| Hybrid | 0.8 | 1 | 1 | 0.9 | 4.6 |

在这个合成 Fixture 中，Hybrid 相比 Text 的 Recall@1/3/5 与 MRR@10 均为 `+0.2`。这些数字
只证明固定 Corpus、指标计算和融合实现可复现，不代表 `nomic-embed-text` 的真实仓库质量。

## 4. Semantic SQL 与端到端耗时

初始 Semantic SQL 在 `LIMIT` 前连接 Chunk/File/Symbol/Commit 元数据，真实 Plan 约
`895.552 ms`、8,441 shared buffers。优化后先在固定 `embedding_index_id` 内执行向量距离排序并
截取候选，再加载元数据：

- 冷态 Plan：`41.772 ms`。
- 热态 Plan：`2.5–3.1 ms`，约 3,613 shared buffers。
- 真实 Ollama Hybrid 连续 20 次：p50 `56 ms`、p95 `69 ms`、平均 `106 ms`；首次冷请求最大
  `1.043 s`。

Plan 复验使用专用临时 `tmpfs` PostgreSQL 只读副本，并关闭 `fsync`，目的是隔离当时机器的磁盘
与内存压力；它不是正式持久化部署配置。正式验收数据仍保存在默认持久化配置的
`repovista_v04_acceptance`。机器仅 8 GiB，复验时系统 Swap 曾约为 11.1/12 GiB；旧持久化容器
在系统压力下进入 PostgreSQL crash recovery，不能据此宣称 SQL 数据损坏。
