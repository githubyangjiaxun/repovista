# RepoVista v0.9 开发计划：Verified Guardrail Explanations

状态：已完成（2026-08-25）
目标版本：`0.9.0`

## 1. 版本目标

v0.9 在 v0.8 不可变 Guardrails Policy Profiles 之上增加可选的 AI 解释层。用户可以针对一个已经由确定性规则产生的 Finding 请求解释，但 AI 不参与规则计算、严重级别、指纹、策略绑定、Commit 选择或证据定位。

## 2. 交付范围

- 为指定 Ready Snapshot 的指定 Finding 生成解释。
- 解释请求只能引用服务端重新计算的 Finding，客户端不能提交 Finding 正文冒充事实。
- 服务端根据 Finding 的固定 evidence range 读取同一 Snapshot 的源码片段，构造有界 Evidence。
- AI 输出经过现有 citation verifier 校验；不存在于 Evidence 的 citation 会被移除，完全无引用的答案自动变为 `refused`。
- 返回并持久化固定 provenance：Snapshot、Commit、parser、Guardrails algorithm、Profile fingerprint、Finding fingerprint、provider、model 和 prompt 版本。
- 相同 Snapshot/Finding/provider/model/prompt 版本请求幂等复用不可变结果；不会原地更新解释。
- 不保存原始模型响应或完整源码文件；仅保存 verifier 接受的有界 citation 摘录，供用户复核。
- API、CLI、Web 展示解释和证据跳转；公开资源不泄露 Workspace 私有数据。

## 3. 明确不做

- AI 不生成或修改 Guardrail 规则、阈值、Prompt 配置或模型配置。
- 不接受客户端上传的源码、Finding JSON、脚本或任意 Prompt。
- 不把自然语言解释当作 CI 阻断依据；CI 仍只依据确定性 Guardrails JSON/SARIF。
- 不宣称 AI 解释是安全证明、修复补丁或真实模型质量评测。

## 4. 验收标准

1. API 能拒绝不存在、非 Ready、跨 Snapshot 或跨 Workspace 的 Finding。
2. AI 返回的 citation 只能来自指定 Snapshot 的固定文件和行范围。
3. 供应商失败、非法 JSON、无证据和超时都有结构化错误或 `refused` 结果。
4. 数据库唯一键保证同一请求复用；历史解释保留且不能被新策略或新 Snapshot 改写。
5. API 契约、CLI、Web、单元测试、数据库集成测试、E2E 和发布文档同步。
