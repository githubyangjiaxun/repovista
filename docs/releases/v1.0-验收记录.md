## 1. 交付内容

v1.0 将 v0.9 的单条 Verified Guardrail Explanation 扩展为跨 Snapshot 的只读历史和纯结构比较。
历史与比较都只读取已经通过 v0.9 citation verifier 的不可变记录，不调用 AI、不写入新的解释，也不
把文本差异解释成质量、回归或改进。

- 新增服务端 `guardrailFindingSubjectKey`，与 Guardrails baseline 配对规则共用六类确定性身份
  逻辑，输出 `sha256:<64 hex>`。
- 新增 Migration `0008_guardrail_explanation_history.sql`：回填 v0.9 `finding_json`、设置非空和
  SHA-256 格式约束，并建立 `(workspace_id, subject_key, created_at DESC, id DESC)` 历史索引。
- 新增 `GET /v1/snapshots/{snapshotId}/guardrails/explanations`，从服务端重算当前 Finding 后按
  opaque cursor 返回同 Repository/Workspace 的有界摘要。
- 新增 `GET /v1/repositories/{repositoryId}/guardrails/explanations/compare`，对两条同逻辑
  Finding 的完整解释比较 provenance、Finding 和 Answer 字段，只返回 `same/changed`。
- CLI 新增：
  `guardrails explanations history <snapshot-id> <finding-id>`；
  `guardrails explanations compare <repository-id> <base-id> <head-id>`。
- Web Finding 卡片新增按需历史、Load more、Base/Head 选择、结构差异矩阵、Viewer 只读访问和
  各自 Snapshot 的固定 Citation 跳转；请求序号防止切换 Snapshot/分页后的旧响应覆盖当前状态。
- OpenAPI 从 59 增加到 61 operations；全 Workspace package、CLI、SARIF 默认工具和 OpenAPI
  版本统一为 `1.0.0`。

## 3. 独立 PostgreSQL 验收

为避免触碰已有数据，使用现有 PostgreSQL 容器创建临时数据库
`repovista_v1_test_20260825`，只运行集成测试，随后立即删除该数据库：

```text
docker exec repovista-postgres-1 createdb -U repovista repovista_v1_test_20260825
DATABASE_TEST_URL=postgresql://repovista:***@127.0.0.1:65432/repovista_v1_test_20260825 \
  pnpm --filter @repovista/database test
docker exec repovista-postgres-1 dropdb -U repovista repovista_v1_test_20260825
```

结果：`store.integration.test.ts` 11/11 通过。覆盖 Migration 0001～0008、`subject_key` 回填
约束、同时间戳 cursor 无重复/无遗漏、非法 cursor、同逻辑 Finding 历史摘要和 Explanation Pair。
没有读取、清空或写入默认 `repovista` 数据库。

另外单独验证了真实升级路径：创建临时数据库后只应用 Migration 0001～0007，插入一条符合 v0.9
结构的旧 `guardrail_explanations` 记录，再执行 `pnpm --filter @repovista/database migrate` 应用
0008。迁移生成的 `subject_key` 与 `guardrailFindingSubjectKey` 的 SHA-256 结果逐字一致；另外使用
包含 `|` 和引号的身份字段验证了规范 JSON 编码不会发生分隔符碰撞。`schema_migrations` 正确记录
0008；临时数据库随后删除。该验证不触碰默认数据库。

## 4. 权限与可信边界

- 历史入口先做 Snapshot Access，再从服务端固定 Snapshot/Profile 重算 Finding；客户端不能提交
  `subjectKey`、Finding JSON、Rule、Repository 或源码。
- Store 查询同时限定 Workspace 和 Repository；跨 Workspace、跨 Repository、缺失解释和不同
  `subjectKey` 不泄露记录存在性。
- Viewer 可以读取历史和比较，但不能生成新解释；生成仍沿用 v0.9 CSRF、写权限和限流边界。
- 比较不调用 Provider，不产生 audit create 事件，不输出 `improved/regressed/winner`，只呈现
  结构化 `same/changed`。
- 私有响应使用 `Cache-Control: private, no-store`；公开 Demo 使用
  `public, max-age=0, must-revalidate`。
- Fake Provider 和测试 Fixture 只证明协议、持久化与边界，不证明真实外部模型质量；本次未使用
  真实外部模型账户或真实私有 GitHub Fixture。

## 6. 已知边界

- 历史按解释创建时间排序，不代表代码变好或变坏；比较是结构差异，不是语义质量评估。
- `subjectKey` 是查询索引，不是授权边界；所有权限仍依赖 Workspace/Repository/Snapshot Access。
- 两个相同的新解释请求在模型调用前可能同时到达，数据库持久化强幂等，但供应商费用的分布式
  single-flight 仍是未来工作。
- Cursor 是有界 opaque 值，记录删除/保留策略尚未提供公开 API。
