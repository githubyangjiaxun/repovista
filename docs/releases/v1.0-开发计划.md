# RepoVista v1.0 开发计划：Guardrail Explanation History

状态：已完成并通过发布门禁（2026-08-25）
目标版本：`1.0.0`

## 1. 版本目标

v1.0 把 v0.9 的单条 Verified Guardrail Explanation 扩展为可审计历史。用户可以从当前
确定性 Finding 出发，查看同一 Repository 中同一逻辑 Finding 在不同不可变 Snapshot 上保存的
解释，并对任意两条历史解释执行纯代码、可复现的字段比较。

历史查询和比较都不会调用模型。模型只负责 v0.9 已定义的单次解释；v1.0 只读取已经经过 citation
verifier 并持久化的结果。

## 2. 交付范围

- 为每条解释保存服务端计算的 `subjectKey`，用于跨 Snapshot 识别同一逻辑 Finding。
- 迁移并回填已有 v0.9 解释，不修改其 Finding、Answer、Citation 或 provenance。
- 以当前 Snapshot 的真实 `findingId` 为入口分页读取同 Repository、同 Workspace 的解释历史。
- 历史列表只返回有界摘要；完整解释仍通过现有详情接口读取。
- 对同一 `subjectKey` 的两条解释执行确定性比较，返回 provenance、Finding 和 Answer 的精确字段变化。
- 比较明确显示 Commit、parser、algorithm、Profile、provider/model 和 prompt 是否变化，不把文本差异解释为质量提升或退化。
- CLI 提供历史列表与比较命令；Web 在 Finding 卡片内提供按需历史面板和两版本比较。
- 同步 Contract、OpenAPI、API/CLI/Web/数据库测试、E2E、README、Changelog 和发布证据。

## 3. 明确不做

- 不让模型总结、评判或合并两条历史解释。
- 不提供解释编辑、删除、重新标记、人工评分或“最佳答案”选择。
- 不用模型文本相似度自动判断 Finding 是否相同。
- 不允许客户端提交 `subjectKey` 来绕过当前 Snapshot/Finding 校验。
- 不跨 Repository、Workspace 或不同逻辑 Finding 比较。
- 不宣称文字变化代表代码质量、模型质量或安全性的变化。

## 4. 完成标准

1. `subjectKey` 与 Guardrails 基线比较使用同一确定性配对规则，并能正确回填 v0.9 数据。
2. 历史 API 使用稳定 cursor 分页；相同时间戳下仍无重复、无遗漏。
3. 历史查询从服务端重算当前 Finding，客户端不能伪造 Repository、Rule 或逻辑身份。
4. 比较 API 拒绝跨 Workspace、跨 Repository、缺失记录和不同 `subjectKey`。
5. 比较结果由结构化值的稳定序列化产生，不调用 Provider，不生成自然语言结论。
6. Viewer 可读取有权限的历史和比较；生成新解释仍沿用 v0.9 写权限、CSRF 与限流。
7. API、CLI、Web、数据库迁移、E2E、Compose、Git 和远端 CI 全部通过后才能发布。
