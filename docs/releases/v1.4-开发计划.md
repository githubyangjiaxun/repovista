# RepoVista v1.4 开发计划：批量 Review 与通知适配器

目标版本：`1.4.0`

v1.4 延续 v1.3 的协作边界：Guardrail Finding 和报告仍由确定性代码生成，Review 只是
Workspace 元数据，通知只是异步外发。此版本解决两个实际使用痛点：一次处理一组 Finding，
以及在不复制业务逻辑的前提下向通用 Webhook/Slack 接收端发送合适的消息格式。

## 用户价值

- 维护者可以在一个原子请求中确认、接受风险、标记误报或清除最多 50 个 Finding。
- 重试批量请求不会重复写入 Review 或产生重复通知；同一个幂等键和不同请求内容会被拒绝。
- 通知 Endpoint 可以选择 `generic` 或 `slack` 适配器。历史 Delivery 保存适配器快照，Endpoint
  后续修改不会改变已经排队的消息。
- Slack 消息只展示事件摘要和状态变化，不泄露 Review 备注、源代码、模型输出或密钥。

## 交付范围

1. 共享 Contract：批量请求/响应、批量事件、`NotificationAdapter` 和新增事件类型。
2. 前向 Migration `0011_batch_reviews.sql`：批量幂等记录、Endpoint/Delivery 适配器快照和事件约束。
3. `POST /v1/snapshots/{snapshotId}/guardrails/reviews/batch`，最多 50 项，单事务全有或全无。
4. API/CLI/Web 的批量 Review 操作、幂等键和原子失败反馈。
5. `packages/notifications` 适配器注册、Generic 原样输出、Slack Incoming Webhook payload 渲染和 URL 校验。
6. Worker 按 Delivery 快照选择适配器，继续使用 HMAC 签名、SSRF 防护、超时和重试。
7. Endpoint API/CLI/Web 增加适配器选择；OpenAPI、测试、运维与验收文档同步。

## 非目标

- 不批量修改 Guardrail Finding、severity、阈值、报告状态或 CI 退出码。
- 不把 Review 备注正文放入批量审计元数据、通知 payload、Slack blocks 或 AI 请求。
- 不执行用户提供的模板/代码，不引入 Slack/Teams SaaS SDK，不自动创建第三方凭据。
- 不支持跨 Snapshot、跨 Workspace 或跨 Repository 的批量操作。
- 不在浏览器直接请求 Webhook；所有投递仍由 Worker outbox 完成。

## 里程碑与完成定义

### M1 契约与文档

- Contract、OpenAPI、前后端/数据库/AI/运维文档定义同一字段、错误码和隐私边界。

### M2 原子批量 Review

- 服务端从当前 Ready Snapshot 报告重新计算每个 `subjectKey`。
- Finding ID 必须唯一且属于同一个 Snapshot；任何一项无效时数据库无写入。
- `Idempotency-Key`（1–200 个 ASCII 字符）与请求哈希按 Workspace/Snapshot 唯一；相同键和相同
  内容返回原结果，不同内容返回冲突。
- 实际变化逐项写入既有 Review 历史；批量操作额外写入一个不含备注正文的聚合审计事件和一个
  `guardrail_review.batch_updated` outbox 事件。未变化项不写审计/通知。

### M3 通知适配器

- `generic` 保持 v1.3 JSON 结构兼容。
- `slack` 输出 Incoming Webhook 可接受的 `text` 与 `blocks`，内容只来自服务端事件摘要。
- Slack URL 必须 HTTPS，主机仅允许 `hooks.slack.com` 或 `hooks.slack-gov.com`；禁止凭据、Fragment、
  私网/loopback/元数据地址和重定向。
- Delivery 持久化 `adapter` 快照；Worker 不接受任意用户代码或动态 import。

### M4 质量门禁

- OpenAPI、Biome、TypeScript、单元/API/数据库集成、Web、CLI、E2E、构建、Benchmark、Git 完整性和
  远端 CI 全部通过。
- 不声称已联调真实 Slack、真实私有 GitHub App 或外部模型；仅报告可复现的本地假适配器测试。
