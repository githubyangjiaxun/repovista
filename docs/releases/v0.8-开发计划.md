# RepoVista v0.8 开发计划：Guardrails Policy Profiles

状态：已实现并验收
目标版本：`0.8.0`

## 1. 版本主题

v0.8 在 v0.7 Snapshot 基线比较之上增加可审查、版本化的 Guardrails Policy
Profiles。策略只能选择已定义规则的阈值，不能增加任意脚本、执行代码或让 AI
决定问题。

## 2. 用户价值

1. 团队可以为不同仓库使用 `default`、`strict` 或自定义阈值。
2. 每个 Snapshot 固定记录当时使用的策略版本，历史报告可重现。
3. 策略变更通过新版本实现，保留旧版本和可审查的指纹。
4. 基线比较会拒绝不同策略指纹，避免把阈值改变误认成代码改善。

## 3. 交付范围

### 3.1 策略模型

- 系统内置 `default` 策略；自定义策略按 Workspace 隔离。
- 策略由 `profileKey` + 自增 `version` 标识，每个版本有独立 UUID 和指纹。
- 只允许已定义的 `cycleMaxLength`、`largeFileLines`、`largeFileBytes`、
  `largeSymbolLines` 和 `highFanIn`。
- 创建内容与最新版本完全相同的请求幂等复用既有版本；名称、描述或阈值变化时才创建下一版本。
  版本不允许原地修改或删除。
- 仓库绑定具体策略版本；创建新 Snapshot 时将策略 ID 写入 Snapshot。

### 3.2 HTTP API

```http
GET  /v1/guardrail-profiles
POST /v1/guardrail-profiles
GET  /v1/guardrail-profiles/{profileId}
GET  /v1/repositories/{repositoryId}/guardrail-profile
PUT  /v1/repositories/{repositoryId}/guardrail-profile
```

`POST /v1/guardrail-profiles` 不是可变更新：同一 `profileKey` 的内容变化请求会产生新版本，
完全相同的最新版本请求幂等复用既有记录。服务器根据已验证的字段计算指纹。所有读取都遵循现有
Workspace 权限。

### 3.3 报告与比较

- `GuardrailReport.profile` 返回策略 ID、key、version、algorithm 和 fingerprint。
- `Snapshot.guardrailProfileId` 保留该 Snapshot 创建时的策略快照。
- 比较只允许策略 fingerprint 相同的报告；不兼容时返回 HTTP 409。
- 旧 Snapshot 中为 `NULL` 的策略 ID 视为系统内置 `default` 版本。

### 3.4 CLI 与 Web

- CLI 提供 `guardrails profiles` 查看策略、`guardrails profile create` 创建新版本、
  `guardrails profile assign` 绑定仓库，以及原有报告/比较命令。
- Web Guardrails 页显示 Snapshot 实际策略和指纹；拥有写权限时可从现有策略中切换仓库默认策略。
- 切换只影响新创建的 Snapshot，不修改历史报告。

## 4. 非目标

- 不允许用户上传代码执行脚本或自定义规则。
- 不让 AI 调整阈值、提升 Finding 或绕过权限。
- 不在本版实现自动 PR 阻断、策略审批流程或策略删除。

## 5. 完成定义

- 旧 Snapshot 在策略切换后仍产生完全相同的报告。
- 同一 `profileKey` 的新版本具有可验证的自增版号和指纹。
- 跨 Workspace 的策略 ID 不可探测；无权限资源返回稳定 404。
- 不同策略指纹的基线比较返回稳定 409，不返回源码正文。
- OpenAPI、README、CHANGELOG、Roadmap、前后端/数据库/运维文档和验收记录同步。

## 6. 实施阶段

1. Contracts 与纯函数 profile fingerprint/provenance。
2. 数据库迁移、Snapshot 快照和 Store 版本化操作。
3. API 权限、创建/列出/绑定和策略兼容性比较。
4. CLI 策略工作流程和 Web 策略展示/切换。
5. OpenAPI、测试、版本、发布证据、Git 提交与 Push。
